# apps/admin — لوحة الإدارة

لوحة تحكم العمليات: العملاء، الفنيين، الطلبات، الأرباح، الشكاوى، الإحصائيات. الستاك: **Next.js 16 (App Router) + shadcn/ui (radix base) + Tailwind v4**، RTL بالكامل (`lang="ar" dir="rtl"`).

## الحالة الحالية — الشاشات الأساسية كلها موجودة ومختبرة حي

تسجيل دخول OTP كامل + حماية المسارات (`proxy.ts`) + كل الشاشات المخطط ليها أصلاً، كل واحدة فيها مختبرة حي (Playwright ضد الباك-إند الحقيقي شغال على Postgres حقيقي، مش mocks):

- **نظرة عامة** (`/`) — `DashboardStats` حقيقية.
- **الموظفين** (`/employees`) — قايمة + إنشاء + تفاصيل (تعديل، حظر/إلغاء حظر، الأدوار، آخر الدخولات، آخر الأنشطة).
- **العملاء** (`/customers`, `/customers/:userId`) — شاشة جديدة، كانت فجوة مكتشفة (مش موثّقة صراحة قبل كده) لقيناها بمقارنة كنترولرز `/admin` الموجودة في الباك-إند بصفحات `apps/admin/src/app` — `admin-customers.controller.ts` كان موجود ومختبر من زمان (قايمة مفلترة بالحظر/الفئة/رقم الموبايل، تفاصيل، حظر/فك حظر) من غير أي شاشة تستخدمه خالص، عكس نفس النمط بالظبط الموجود بالفعل للموظفين. الشاشة الجديدة مطابقة تماماً لنمط `/employees`: قايمة بفلتر (نشط/محظور + بحث برقم الموبايل) + تفاصيل (الفئة، إحصائيات الطلبات، إجمالي الإنفاق، رصيد نقاط الولاء، حظر بسبب إلزامي/فك حظر). `AdminCustomerResponseDto`/`BlockCustomerBody` جداد في `@baytak/shared-types`. **اتعمله اختبار حي كامل عبر Playwright**: القايمة عرضت عميل الاختبار الحقيقي، التفاصيل عرضت بياناته صح، حظره نجح وظهر البادچ "محظور" + سبب الحظر بالنص المكتوب، فك الحظر رجّعه "نشط" — اتأكد الحالة النهائية مباشرة من الـ DB (`users.is_blocked=false`, `blocked_reason=null`) مش بس من الشاشة.
- **الفنيين** (`/technicians`) — قايمة بفلتر الحالة + تفاصيل (اعتماد/رفض، تغيير المستوى، مراجعة المستندات، **مناطق العمل** — كارت جديد، كانت فجوة موثّقة في `apps/api/src/modules/technicians/README.md` ("technician_zones يدوي عبر SQL")، اتقفلت: اختيار منطقة من قايمة كل النطاقات (`GET /admin/service-zones`) + تبديل "أساسية" + إضافة، وجدول بالمناطق الحالية مع زرار إزالة لكل واحدة. اتعمله اختبار حي عبر Playwright: تعيين منطقة نجح وظهرت بالاسم الصح في الجدول، الإزالة نجحت والجدول رجع لرسالة "مفيش مناطق" الفارغة، اتأكد الاتنين مباشرة من الـ DB مش بس من الشاشة. **زرار "الخطوة الجاية" لمسار التحقق الوسيط** — كانت فجوة موثّقة تانية في نفس ملف الباك-إند README (الحالات الوسيطة `documents_submitted`/`under_review`/`interview_scheduled`/`test_passed` معرّفة بس مفيش endpoints تحرّك الفني بينهم)، اتقفلت في الباك-إند الأول (4 endpoints جديدة `POST /admin/technicians/:id/mark-*` و`schedule-interview`) وبعدين هنا: زرار واحد جنب "اعتماد"/"رفض" بيتغيّر لبيله ووجهته حسب `NEXT_VERIFICATION_STEP` في `src/lib/technician-labels.ts` (خريطة حالة → endpoint + نص عربي)، بيفتح `window.prompt()` لملاحظة اختيارية (لو دوس المستخدم "إلغاء" في الـ prompt بيتلغي الإجراء كله مش يكمل بملاحظة فاضية)، وبيختفي تلقائي لما الفني يوصل `test_passed` (مفيش خطوة جاية بعدها غير اعتماد/رفض يدوي). اتعمله اختبار حي كامل عبر Playwright: فني اتسجّل بعمولة API مباشرة، الأربع ضغطات اتعملت بالترتيب (`pending`→`documents_submitted`→`under_review`→`interview_scheduled`→`test_passed`)، اتأكد بعد كل خطوة من تغيّر البادج والزرار في الشاشة، ومن الـ DB مباشرة (`technician_profiles.verification_status` + `audit_logs` فيها الملاحظة المكتوبة في كل الأربع صفوف)، والزرار اختفى صح بعد `test_passed`.
- **الطلبات** (`/orders`) — قايمة بفلتر سريع + تفاصيل (تاريخ الحالة، إلغاء، إعادة تعيين فني، صور قبل/بعد، **بنود عرض السعر** — تفاصيل تحت).
- **الكتالوج** (`/catalog`) — الفئات والخدمات: قايمة + إنشاء + تفعيل/تعطيل. اسم كل خدمة رابط لـ**شاشة تفاصيلها** (`/catalog/services/:id` — كانت فجوة موثّقة، اتقفلت): تسعير حسب المنطقة، الفنيين المؤهلين (بالاسم الحقيقي، مش UUID)، تسعير حسب مستوى الفني، والإضافات الاختيارية — الأربعة كانوا API-only بالكامل قبل كده. أثناء البناء اتلقطت واتصلحت بَقّة حقيقية في الباك-إند: `zone-pricing`/`technicians` كانوا بيرجّعوا JSON بـ camelCase (entity خام) بدل الـ`snake_case` المتّبع في كل مكان تاني في الـ API — تفاصيل كاملة في `apps/api/src/modules/catalog/README.md`.
- **`المدن والمناطق` (`/geo`) — كانت فجوة موثّقة صراحة في `apps/api/src/modules/geo/README.md` (الـ CRUD كان API-only تماماً، مفيش شاشة تستخدمه)، اتقفلت**: المدن (قايمة + إنشاء بإحداثيات مركز اختيارية + تفعيل/تعطيل)، وبعد اختيار مدينة من الجدول: مناطقها (إنشاء + تبديل "مُطلَقة") ونطاقات خدمتها (إنشاء + مضاعف الذروة + تفعيل/تعطيل + عرض حالة المضلّع). إنشاء مدينة محتاج اختيار دولة — استلزم إضافة `GET /admin/countries` (قراءة بس، جديدة في الباك-إند، تفاصيل في `geo/README.md`) لأنها ماكانتش موجودة خالص قبل كده. **رسم مضلّع تغطية النطاق (`ZoneBoundaryMap`) — كانت فجوة موثّقة صراحة ("مفيش لوحة رسم خرائط تفاعلية")، اتقفلت**: زرار "رسم مضلّع"/"تعديل المضلّع" جنب كل نطاق خدمة بيفتح لوحة خريطة تفاعلية تحت الجدولين مباشرة. الخريطة مبنية بـ `leaflet` الخام (مش `react-leaflet` — تعمّدنا تجنّب باينـدنج React لأن React 19 لسه مش متأكدين من توافقه معاه، فاستخدمنا `useEffect`/`useRef` عاديين وناديت `L.map()` مباشرة) وبلاطات **OpenStreetMap** (`tile.openstreetmap.org`، مجانية بالكامل من غير أي API key — عكس Google Maps المستخدمة في تطبيقات Flutter، مفيش حتى placeholder محتاج قيمة هنا). دوس على الخريطة يضيف نقطة (دائرة صغيرة + تحديث خط المضلّع لحظياً)، وفيه "تراجع عن آخر نقطة"/"مسح الكل"/"حفظ المضلّع" (معطّل لحد 3 نقط على الأقل). فتح اللوحة بيحمّل المضلّع الحالي أول حاجة لو موجود (endpoint جديد بالباك-إند `GET /admin/service-zones/:id/boundary` بيرجّع نقط خام مش GeoJSON خام، تفاصيل في `geo/README.md`) عشان تقدر تعدّل مضلّع موجود مش بس ترسم واحد جديد من الصفر. الحفظ بيستخدم `PUT /admin/service-zones/:id/boundary` الموجود من قبل كده. **اتعمله اختبار حي كامل عبر Playwright**: نطاق تجريبي من غير مضلّع، فتح اللوحة، 4 نقط اتضافت بالنقر الفعلي على الخريطة (مش إحداثيات مُدخلة يدوي)، "تراجع" شال آخر نقطة (4→3 اتأكد من نص العدّاد)، إعادة إضافتها، الحفظ نجح واللوحة اتقفلت وعمود "مضلّع مرسوم؟" اتحدّث لـ"مرسوم" فوراً — اتأكد المضلّع النهائي مباشرة من الـ DB (`ST_AsGeoJSON`): حلقة مقفولة صح (4 نقط مميزة + نقطة إغلاق تلقائية مطابقة للأولى)، وبإعادة قراءة `GET .../boundary` رجعت نفس النقط بالظبط للتعديل. **قيد اختبار صريح لبيئة الـ sandbox دي تحديداً (مش بَقّة في الكود)**: بروكسي الشبكة في بيئة التطوير دي بيمنع الوصول لأي دومين مش على قايمة سماح محددة (اتأكد بمحاولة `curl` مباشرة لـ`tile.openstreetmap.org` فرجعت رفض من البروكسي، زي ما بيرفض `google.com` كمان) — يعني بلاطات الخريطة (الصور الفعلية) متقدرش تتحمّل فعلياً هنا للتأكد البصري منها، نفس فئة القيد الموثّقة في `apps/customer-app/README.md` لعدم القدرة على اختبار الـ widgets الفعلية. المنطق التفاعلي كله (تحويل نقرة الماوس لإحداثية lat/lng، الرسم، الحفظ، القراءة) مستقل تماماً عن تحميل صور البلاطات واتأكد منه بالكامل حياً زي ما فوق — بس شكل الخريطة الجغرافي الفعلي (الشوارع/المباني) لسه محتاج بيئة إنتاج حقيقية بوصول إنترنت كامل عشان يتأكد منه بصرياً.
- **الإعدادات** (`/settings`) — محرر مجموعات مفتاح/قيمة حسب النوع (boolean/number/string/JSON).
- **سجل النشاط** (`/audit-log`) — قايمة بفلتر + عرض تفاصيل old/new values.
- **`Feature Flags` (`/feature-flags`) — كانت فجوة موثّقة صراحة في `apps/api/src/modules/feature-flags/README.md` ("مفيش استهلاك من apps/admin لسه")، اتقفلت**: قايمة كل الفلاجز + إنشاء (مفتاح + وصف اختياري، بيبدأ `is_enabled=false`/`rollout_percentage=0` دايماً — تفعيل صريح بعد المراجعة، مش افتراضي)، تبديل الحالة (badge قابلة للنقر، نفس نمط `is_active` في الكتالوج)، تعديل نسبة التوزيع inline (نقر على النسبة → input رقمي 0-100 → حفظ)، وحذف. **الاستهداف الصريح** (`enabled_for_user_ids`/`enabled_for_zone_ids`) — كان معروض للقراءة بس، تعديله محتاج الـ API مباشرة (فجوة موثّقة)، اتقفلت: نقر على عمود "الاستهداف الصريح" لأي فلاج بيفتح لوحة تعديل جوّه الجدول (صف موسّع)، فيها قسمين — مستخدمين محدّدين (إدخال UUID خام مع تحقق بسيط بـ`regex` قبل الإرسال + شارة قابلة للحذف لكل واحد) ومناطق خدمة محدّدة (`<select>` من `GET /admin/service-zones` بالاسم العربي بدل UUID خام، نفس نمط "مناطق العمل" في `technicians/[id]`). كل إضافة/حذف بترسل `PATCH` بالمصفوفة الكاملة الجديدة (الـ endpoint بيستبدل المصفوفة مش بيعمل append/remove جزئي). **اتعمله اختبار حي كامل عبر Playwright**: فلاج تجريبي جديد، فتح لوحة الاستهداف، إضافة UUID عميل حقيقي (ظهر كشارة)، إضافة منطقة حقيقية من القايمة (ظهرت باسمها العربي)، حذف شارة المستخدم (اختفت، المنطقة فضلت)، اتأكد الأربعة من الـ DB مباشرة (`feature_flags.enabled_for_user_ids`/`enabled_for_zone_ids`) مش بس من الشاشة، و`audit_logs` سجّل كل تعديل. **بَقّة اختبار (مش في التطبيق) اتلقطت أثناء البناء**: أول نسخة من سكريبت الاختبار استخدمت `getByRole('button', {name: 'إضافة'})` من غير `exact: true` ومن غير تحديد النطاق (scope) للوحة الصح — طابقت أزرار "إضافة استهداف" التبديلية في صفوف تانية بالخطأ (تطابق جزئي للنص)، فبدت المنطقة وكأنها اتضافت وهي في الحقيقة لأ (فحص نصّي ساذج للصفحة كله رجّع `true` كاذبة). اتصلحت بتحديد اللوكيتورز على صف اللوحة نفسها وفحص عنصر الـ`Badge` (`data-slot="badge"`) مباشرة بدل نص الصفحة العام، وبعدها الفحص من الـ DB أكّد إن الميزة نفسها شغالة صح من الأول.

**صور الطلب (`/orders/:id`) — كانت فجوة موثّقة، اتقفلت**: قسم "صور الطلب" في تفاصيل الطلب بيعرض كل الصور المرفوعة (`GET /admin/orders/:id/media` — endpoint جديد اتضاف، الأدمن مكانش عنده أي طريقة يشوف صور قبل/بعد قبل كده، تفاصيل كاملة في `../api/src/modules/orders/README.md`) — grid صور بعنوان (قبل/بعد/إلخ) وتعليق، كل صورة بتفتح في تاب جديد بالحجم الكامل. **بَقّة حقيقية أعمق اتلقطت واتصلحت وقت بناء الميزة دي**: الصور مكانتش بتظهر أصلاً — `LocalDiskStorageService` في الباك-إند بيكتب الملفات فعلياً بس مفيش حاجة كانت بتخدمها فوق HTTP (رابط `/uploads/...` كان 404 دايماً من اليوم الأول). اتصلح في `apps/api/src/main.ts` (`useStaticAssets`)، اتأكد الإصلاح حياً (curl مباشر رجّع الصورة صح) **وبصرياً** (Playwright — سجّل دخول حقيقي، فتح تفاصيل طلب حقيقي فيه صورتين حقيقيتين اترفعوا من اختبار حي سابق في `apps/technician-app`، الصورتين ظهرتا فعلاً بعنوانيهم وتعليقهم الصح).
- `type OrderMediaResponseDto` اتضاف لـ `@baytak/shared-types` (`packages/shared-types/src/orders.ts`) مطابق لـ `order-media-response.dto.ts`.

**بنود عرض السعر (`/orders/:id`) — كارت جديد للقراءة بس**: أضيف مع مسار `order_items`/`awaiting_quote_approval` نفسه في الباك-إند (كانت فجوة موثّقة صراحة، اتقفلت — تفاصيل كاملة والاختبار الحي في `apps/api/src/modules/orders/README.md`). بيعرض `GET /admin/orders/:id/quote-items` (endpoint جديد اتضاف، نفس نمط `.../media`): اسم البند مع الكمية × سعر الوحدة تحته، النوع (قطعة غيار/أجرة إضافية/إضافة)، الإجمالي، وبادچ "موافَق عليه"/"معلّق". عشان الدعم الفني/العمليات يراجعوا البنود الإضافية اللي الفني اقترحها من غير API مباشر — مفيش أي إجراء (موافقة/رفض) من هنا، دي مسؤولية العميل بس عبر `apps/customer-app`. `type OrderItemResponseDto` اتضاف لـ `@baytak/shared-types`. اتأكد حياً عبر Playwright على نفس الطلب اللي اتعمله فيه الاختبار الحي في الباك-إند (بندين معتمدين، 30000+8000=38000 قرش بالظبط) — الكارت ظهر بالبيانات والبادچ الصح.

**فجوات موثّقة صراحة داخل الشاشات الموجودة** (مش سهو — كل واحدة موثّقة في مكانها؛ تسعير المناطق/الفنيين المؤهلين للكتالوج وسباق التابات في الـ auth كانوا هنا، اتقفلوا — تفاصيل تحت):
- ~~الكتالوج: باقي حقول الخدمة التفصيلية~~ — **اتقفلت**: كارت "تفاصيل الخدمة" جديد فوق الأقسام الأربعة في `/catalog/services/:id` بيدي تعديل الوصف المختصر، أقل/أعلى سعر، أيام الضمان، المدة المتوقعة، ومحتاجة صور/حجز مجدول/طلب طارئ — كل ده كان محتاج `PATCH /admin/services/:id` مباشر عبر الـ API قبل كده. اتعمله اختبار حي: تعديل الحقول الستة كلها، إعادة تحميل الصفحة كاملة، وتأكيد إن كل قيمة اتحفظت صح من الـ DB (مش state محلي بس).

**بَقّة حقيقية اتلقطت واتصلحت في `/orders/:id` — زرار "إعادة تعيين فني" كان مستحيل الاستخدام عملياً**: الشرط القديم لعرض الزرار كان `order.technician_id` (يعني: اعرض الزرار بس لو فيه فني معيّن بالفعل). لكن الباك-إند (`REASSIGNABLE_STATUSES` في `admin-orders.service.ts`) بيسمح بالتعيين اليدوي **بس** قبل ما أي فني يقبل الطلب (`searching_technician`/`technician_assigned`) — وفي الحالتين دول `technician_id` لسه `null` عملياً (بيتحط لحظة القبول). يعني الزرار كان بيظهر بالظبط في الحالة اللي هيترفض فيها التعيين (409)، ومختفي في الحالة الوحيدة اللي هيشتغل فيها فعلاً — ميزة موجودة في الكود بس مستحيل الوصول لها عبر الواجهة. اتصلحت بـ `isOrderReassignable()` جديدة في `src/lib/order-labels.ts` (مطابقة حرفياً لـ`REASSIGNABLE_STATUSES` في الباك-إند) بدل الشرط القديم. **بالمناسبة اتقفلت الفجوة التانية المعروفة في نفس المكان**: مدخل `technician_id` كان UUID خام بيتكتب يدوي — بقى `<select>` حقيقي بيجيب الفنيين المعتمدين فعلاً (`GET /admin/technicians?verification_status=approved`) بالاسم وكود الفني. **اتعمله اختبار حي كامل**: طلب حقيقي اتعمل وسايبه من غير أي فني يقبله (`searching_technician`)، فتح تفاصيله في `apps/admin` — الزرار ظهر فعلاً هذه المرة (كان مش هيظهر قبل الإصلاح)، القايمة المنسدلة عرضت 3 فنيين معتمدين حقيقيين بالاسم، اختيار واحد وتأكيد التعيين نجح وحوّل الطلب لـ`accepted` بالفني الصح فوراً — اتأكد بصرياً وبقراءة الحالة بعد كل خطوة.

## المعمارية الأمنية للـ auth (مهم قبل ما تلمس أي حاجة هنا)

- **`refresh_token`**: httpOnly cookie، مايوصلش لجافاسكريبت العميل خالص — بيتحط عن طريق Route Handlers فقط (`src/app/api/auth/*`)، دي طبقة BFF (backend-for-frontend) بسيطة بتبروكسي لـ `apps/api`.
- **`access_token`**: قصير العمر (15 دقيقة)، في الذاكرة بس (React state، مش localStorage) — عشان يبقى أقل عرضة لسرقة عبر XSS.
- **باقي نداءات الـ API الحقيقية** (dashboard stats وغيرها) بتتبعت مباشرة لـ `apps/api` من الـ client (`NEXT_PUBLIC_API_URL`)، برفقة `Authorization: Bearer` — مش عن طريق البروكسي، عشان مانكتبش proxy route لكل endpoint.

### بَقّة حقيقية اتلقطت واتصلحت وقت البناء — Single-flight refresh

الباك-إند بيدوّر `refresh_token` على كل استخدام، وأي إعادة استخدام لتوكن اتلغى بيتعامل معاه كسرقة محتملة فبيقفل **كل** جلسات المستخدم فوراً (`revokeAllUserTokens` في `apps/api/.../auth.service.ts`). React Strict Mode (شغال افتراضياً في التطوير) بيعيد تشغيل الـ `useEffect` بتاع فحص الجلسة عند التحميل **مرتين** — لو كل تشغيلة بعتت نداء `/api/auth/refresh` منفصل، التاني كان هيستخدم نفس الكوكي القديم اللي التاني لسه ما دوّرهوش، فيترفض ويقفل حساب الأدمن كله. اتصلح بـ `inFlightRefresh` ref في `src/lib/auth-context.tsx` — أي نداء refresh بيشارك نفس الـ promise "في الطيران" بدل ما يبعت نداء منفصل، فمفيش سباق. اتأكد الإصلاح حياً (login → reload → session لسه شغالة → logout → redirect صحيح).

**فجوة السباق عبر التابات — كانت موثّقة كـ"سباق نادر"، اتقفلت (والتحقيق الحي صحّح الفرضية الأصلية)**: الحل فوق (`inFlightRefresh` ref) بيمنع السباق **جوّه نفس تحميل الصفحة بس** — تابين مفتوحين لنفس الحساب كل واحد عنده React state منفصل تماماً، فمفيش حاجة كانت بتمنعهم الاتنين يبعتوا `/api/auth/refresh` بنفس الكوكي في نفس اللحظة.

اتعمل تحقيق حي مباشر (Playwright، تابين حقيقيين بنفس الـ browser context فبيشاركوا نفس الكوكيز، نداءين متزامنين فعلياً لـ`/api/auth/refresh` عبر `Promise.all`) **قبل** كتابة أي إصلاح، عشان نتأكد من السلوك الفعلي مش نفترضه. النتيجة صحّحت الفرضية الأصلية في التوثيق: السباق **مابيسببش قفل الحساب** زي ما كان متوقّع — `auth.service.ts`'s `refresh()` بيعمل `findOne` عادي من غير `SELECT ... FOR UPDATE` ولا optimistic lock، فتحت READ COMMITTED نداءين متزامنين فعلياً (اتأكد بفرق توقيت 3-9 ميلي ثانية بس في `refresh_tokens.created_at` مباشرة من الـ DB) بيلاقوا نفس الصف لسه `is_revoked=false` ويعدّوا الاتنين، وبيصدروا **زوج توكنز صالح لكل واحد فيهم** بدل ما التاني يترفض — يعني مش "قفل حساب"، لكن "إصدار جلستين صالحتين من توكن واحد" (تضييع/تكرار مصادر، مش خرق أمني حرج). مسار `revokeAllUserTokens('security_breach')` لسه بيشتغل صح لغرضه الحقيقي — إعادة استخدام توكن **اتلغى بالفعل من قبل** (سرقة/replay)، مش الحالة دي.

اتصلح بـ **Web Locks API** (`navigator.locks.request('baytak-admin-refresh-token', ...)`) — قفل حقيقي عبر كل تابات نفس الأصل، مدعوم في كل المتصفحات الحديثة (Chrome 69+, Firefox 96+, Safari 15.4+)، بيسلسل أي محاولات refresh متزامنة بدل ما تتسابق (fallback للسلوك القديم لو المتصفح مايدعمش الـ API، بدل ما ينهار). اتأكد الإصلاح حياً بنفس أسلوب التحقيق (تابين حقيقيين + نداءين متزامنين، وكمان تحميل تاب تاني حقيقي بيعمل silent refresh تلقائي بتوقيت متداخل معاهم — 3 مصادر refresh متزامنة تقريباً): **قبل** الإصلاح، `refresh_tokens.created_at` أظهر صفين بفرق أقل من 10 ميلي ثانية والاتنين `is_revoked=false` (إصدار مزدوج حقيقي، مؤكّد من الـ DB مباشرة)؛ **بعد** الإصلاح، نفس السيناريو بالظبط أنتج سلسلة تدوير متتالية نضيفة (كل محاولة اترفضت أو نجحت بالترتيب، صف واحد بس فضل صالح في النهاية) من غير أي تداخل.

## ملاحظات Next.js 16 (breaking changes حقيقية اتلقطت)

- **`middleware.ts` بقى `proxy.ts`، والدالة اسمها `proxy` مش `middleware`** — الاسم القديم deprecated. اتعمل التحويل هنا باستخدام الـ codemod الرسمي (`npx @next/codemod@canary middleware-to-proxy .`)، مش تخمين.
- `useSearchParams()` محتاج `<Suspense>` boundary عشان الـ static prerendering ينجح في `next build` — لاحظناها لما الـ build فشل على `/login`.

## shadcn/ui بدون شبكة

`ui.shadcn.com` محجوب بسياسة الشبكة في بيئة التطوير اللي اتبنى فيها المشروع ده (403 على CONNECT). المكوّنات في `src/components/ui/` اتكتبت يدوياً (مطابقة لمصدر shadcn المعروف: `button`, `input`, `label`, `card`) بدل ما نعتمد على `shadcn init`/`shadcn add` اللي بيكلموا الشبكة دي. لو الشبكة اتفتحت مستقبلاً، تقدر تستخدم `npx shadcn@latest add <component>` عادي — بس تأكد إنه مش هيكتب فوق الملفات دي بتنسيق مختلف.
