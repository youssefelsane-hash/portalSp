# apps/admin — لوحة الإدارة

لوحة تحكم العمليات: العملاء، الفنيين، الطلبات، الأرباح، الشكاوى، الإحصائيات. الستاك: **Next.js 16 (App Router) + shadcn/ui (radix base) + Tailwind v4**، RTL بالكامل (`lang="ar" dir="rtl"`).

## الحالة الحالية — الشاشات الأساسية كلها موجودة ومختبرة حي

تسجيل دخول OTP كامل + حماية المسارات (`proxy.ts`) + كل الشاشات المخطط ليها أصلاً، كل واحدة فيها مختبرة حي (Playwright ضد الباك-إند الحقيقي شغال على Postgres حقيقي، مش mocks):

- **نظرة عامة** (`/`) — `DashboardStats` حقيقية.
- **الموظفين** (`/employees`) — قايمة + إنشاء + تفاصيل (تعديل، حظر/إلغاء حظر، الأدوار، آخر الدخولات، آخر الأنشطة).
- **الفنيين** (`/technicians`) — قايمة بفلتر الحالة + تفاصيل (اعتماد/رفض، تغيير المستوى، مراجعة المستندات).
- **الطلبات** (`/orders`) — قايمة بفلتر سريع + تفاصيل (تاريخ الحالة، إلغاء، إعادة تعيين فني، صور قبل/بعد — تفاصيل تحت).
- **الكتالوج** (`/catalog`) — الفئات والخدمات: قايمة + إنشاء + تفعيل/تعطيل. اسم كل خدمة رابط لـ**شاشة تفاصيلها** (`/catalog/services/:id` — كانت فجوة موثّقة، اتقفلت): تسعير حسب المنطقة، الفنيين المؤهلين (بالاسم الحقيقي، مش UUID)، تسعير حسب مستوى الفني، والإضافات الاختيارية — الأربعة كانوا API-only بالكامل قبل كده. أثناء البناء اتلقطت واتصلحت بَقّة حقيقية في الباك-إند: `zone-pricing`/`technicians` كانوا بيرجّعوا JSON بـ camelCase (entity خام) بدل الـ`snake_case` المتّبع في كل مكان تاني في الـ API — تفاصيل كاملة في `apps/api/src/modules/catalog/README.md`.
- **`المدن والمناطق` (`/geo`) — كانت فجوة موثّقة صراحة في `apps/api/src/modules/geo/README.md` (الـ CRUD كان API-only تماماً، مفيش شاشة تستخدمه)، اتقفلت**: المدن (قايمة + إنشاء بإحداثيات مركز اختيارية + تفعيل/تعطيل)، وبعد اختيار مدينة من الجدول: مناطقها (إنشاء + تبديل "مُطلَقة") ونطاقات خدمتها (إنشاء + مضاعف الذروة + تفعيل/تعطيل + عرض حالة المضلّع). إنشاء مدينة محتاج اختيار دولة — استلزم إضافة `GET /admin/countries` (قراءة بس، جديدة في الباك-إند، تفاصيل في `geo/README.md`) لأنها ماكانتش موجودة خالص قبل كده. رسم مضلّع تغطية النطاق نفسه لسه محتاج إحداثيات خام عبر الـ API — مفيش لوحة رسم خرائط تفاعلية، فجوة موثّقة متبقية.
- **الإعدادات** (`/settings`) — محرر مجموعات مفتاح/قيمة حسب النوع (boolean/number/string/JSON).
- **سجل النشاط** (`/audit-log`) — قايمة بفلتر + عرض تفاصيل old/new values.
- **`Feature Flags` (`/feature-flags`) — كانت فجوة موثّقة صراحة في `apps/api/src/modules/feature-flags/README.md` ("مفيش استهلاك من apps/admin لسه")، اتقفلت**: قايمة كل الفلاجز + إنشاء (مفتاح + وصف اختياري، بيبدأ `is_enabled=false`/`rollout_percentage=0` دايماً — تفعيل صريح بعد المراجعة، مش افتراضي)، تبديل الحالة (badge قابلة للنقر، نفس نمط `is_active` في الكتالوج)، تعديل نسبة التوزيع inline (نقر على النسبة → input رقمي 0-100 → حفظ)، وحذف. الاستهداف الصريح (`enabled_for_user_ids`/`enabled_for_zone_ids`) بيتعرض للقراءة بس (عدد المستخدمين/المناطق) — تعديله لسه محتاج الـ API مباشرة، فجوة موثّقة أصغر. **اتعمله اختبار حي كامل عبر Playwright ضد الباك-إند الحقيقي**: تسجيل دخول `super_admin` حقيقي، إنشاء فلاج تجريبي، تفعيله، تعديل نسبة التوزيع لـ42%، وحذفه — كل خطوة اتأكد منها بقراءة نص الصف فعلياً بعد كل عملية، وبمطابقة `audit_logs` مباشرة (الحالة والنسبة فضلوا متسقين عبر تعديلين متتاليين، الحذف اتسجّل صح). أول تشغيلة للاختبار طلعت لقطة شاشة نهائية فيها الحالة ظاهرة "معطّل" رغم إن الـ DB كانت `is_enabled=true` وقتها — اتحقق منها بإعادة التشغيل مع تتبّع نص الصف بعد كل خطوة على حدة، ورجعت النتيجة متسقة مع الـ DB في كل مرة؛ اتقيّمت كتأخير عرضي في تسلسل السكريبت نفسه (تايمنج لقطة الشاشة) مش بَقّة حقيقية في الصفحة — التتبّع النصي المباشر بعد كل خطوة (مش لقطة شاشة واحدة في الآخر) هو الدليل الموثوق.

**صور الطلب (`/orders/:id`) — كانت فجوة موثّقة، اتقفلت**: قسم "صور الطلب" في تفاصيل الطلب بيعرض كل الصور المرفوعة (`GET /admin/orders/:id/media` — endpoint جديد اتضاف، الأدمن مكانش عنده أي طريقة يشوف صور قبل/بعد قبل كده، تفاصيل كاملة في `../api/src/modules/orders/README.md`) — grid صور بعنوان (قبل/بعد/إلخ) وتعليق، كل صورة بتفتح في تاب جديد بالحجم الكامل. **بَقّة حقيقية أعمق اتلقطت واتصلحت وقت بناء الميزة دي**: الصور مكانتش بتظهر أصلاً — `LocalDiskStorageService` في الباك-إند بيكتب الملفات فعلياً بس مفيش حاجة كانت بتخدمها فوق HTTP (رابط `/uploads/...` كان 404 دايماً من اليوم الأول). اتصلح في `apps/api/src/main.ts` (`useStaticAssets`)، اتأكد الإصلاح حياً (curl مباشر رجّع الصورة صح) **وبصرياً** (Playwright — سجّل دخول حقيقي، فتح تفاصيل طلب حقيقي فيه صورتين حقيقيتين اترفعوا من اختبار حي سابق في `apps/technician-app`، الصورتين ظهرتا فعلاً بعنوانيهم وتعليقهم الصح).
- `type OrderMediaResponseDto` اتضاف لـ `@baytak/shared-types` (`packages/shared-types/src/orders.ts`) مطابق لـ `order-media-response.dto.ts`.

**فجوات موثّقة صراحة داخل الشاشات الموجودة** (مش سهو — كل واحدة موثّقة في مكانها):
- الكتالوج: تسعير حسب المنطقة، الفنيين المؤهلين لكل خدمة، وباقي حقول الخدمة التفصيلية (الحد الأدنى/الأقصى، الضمان، ...) — مش متاحين من الواجهة لسه.
- الـ auth: سباق نادر عبر تابين مفتوحين لنفس الحساب لسه ممكن (تفاصيل تحت).

**بَقّة حقيقية اتلقطت واتصلحت في `/orders/:id` — زرار "إعادة تعيين فني" كان مستحيل الاستخدام عملياً**: الشرط القديم لعرض الزرار كان `order.technician_id` (يعني: اعرض الزرار بس لو فيه فني معيّن بالفعل). لكن الباك-إند (`REASSIGNABLE_STATUSES` في `admin-orders.service.ts`) بيسمح بالتعيين اليدوي **بس** قبل ما أي فني يقبل الطلب (`searching_technician`/`technician_assigned`) — وفي الحالتين دول `technician_id` لسه `null` عملياً (بيتحط لحظة القبول). يعني الزرار كان بيظهر بالظبط في الحالة اللي هيترفض فيها التعيين (409)، ومختفي في الحالة الوحيدة اللي هيشتغل فيها فعلاً — ميزة موجودة في الكود بس مستحيل الوصول لها عبر الواجهة. اتصلحت بـ `isOrderReassignable()` جديدة في `src/lib/order-labels.ts` (مطابقة حرفياً لـ`REASSIGNABLE_STATUSES` في الباك-إند) بدل الشرط القديم. **بالمناسبة اتقفلت الفجوة التانية المعروفة في نفس المكان**: مدخل `technician_id` كان UUID خام بيتكتب يدوي — بقى `<select>` حقيقي بيجيب الفنيين المعتمدين فعلاً (`GET /admin/technicians?verification_status=approved`) بالاسم وكود الفني. **اتعمله اختبار حي كامل**: طلب حقيقي اتعمل وسايبه من غير أي فني يقبله (`searching_technician`)، فتح تفاصيله في `apps/admin` — الزرار ظهر فعلاً هذه المرة (كان مش هيظهر قبل الإصلاح)، القايمة المنسدلة عرضت 3 فنيين معتمدين حقيقيين بالاسم، اختيار واحد وتأكيد التعيين نجح وحوّل الطلب لـ`accepted` بالفني الصح فوراً — اتأكد بصرياً وبقراءة الحالة بعد كل خطوة.

## المعمارية الأمنية للـ auth (مهم قبل ما تلمس أي حاجة هنا)

- **`refresh_token`**: httpOnly cookie، مايوصلش لجافاسكريبت العميل خالص — بيتحط عن طريق Route Handlers فقط (`src/app/api/auth/*`)، دي طبقة BFF (backend-for-frontend) بسيطة بتبروكسي لـ `apps/api`.
- **`access_token`**: قصير العمر (15 دقيقة)، في الذاكرة بس (React state، مش localStorage) — عشان يبقى أقل عرضة لسرقة عبر XSS.
- **باقي نداءات الـ API الحقيقية** (dashboard stats وغيرها) بتتبعت مباشرة لـ `apps/api` من الـ client (`NEXT_PUBLIC_API_URL`)، برفقة `Authorization: Bearer` — مش عن طريق البروكسي، عشان مانكتبش proxy route لكل endpoint.

### بَقّة حقيقية اتلقطت واتصلحت وقت البناء — Single-flight refresh

الباك-إند بيدوّر `refresh_token` على كل استخدام، وأي إعادة استخدام لتوكن اتلغى بيتعامل معاه كسرقة محتملة فبيقفل **كل** جلسات المستخدم فوراً (`revokeAllUserTokens` في `apps/api/.../auth.service.ts`). React Strict Mode (شغال افتراضياً في التطوير) بيعيد تشغيل الـ `useEffect` بتاع فحص الجلسة عند التحميل **مرتين** — لو كل تشغيلة بعتت نداء `/api/auth/refresh` منفصل، التاني كان هيستخدم نفس الكوكي القديم اللي التاني لسه ما دوّرهوش، فيترفض ويقفل حساب الأدمن كله. اتصلح بـ `inFlightRefresh` ref في `src/lib/auth-context.tsx` — أي نداء refresh بيشارك نفس الـ promise "في الطيران" بدل ما يبعت نداء منفصل، فمفيش سباق. اتأكد الإصلاح حياً (login → reload → session لسه شغالة → logout → redirect صحيح).

**فجوة موثّقة متبقية**: الحل ده بيمنع السباق **جوّه نفس تحميل الصفحة**. لسه مفيش حماية من سباق عبر تابين مفتوحين لنفس الحساب في نفس اللحظة (كل تاب عنده React state منفصل) — سيناريو نادر بس ممكن، والحل الكامل محتاج إما تنسيق بين التابات (`BroadcastChannel`) أو "فترة سماح" في الباك-إند لإعادة استخدام نفس الـ refresh token خلال ثواني قليلة (نمط شائع في أنظمة rotating refresh tokens).

## ملاحظات Next.js 16 (breaking changes حقيقية اتلقطت)

- **`middleware.ts` بقى `proxy.ts`، والدالة اسمها `proxy` مش `middleware`** — الاسم القديم deprecated. اتعمل التحويل هنا باستخدام الـ codemod الرسمي (`npx @next/codemod@canary middleware-to-proxy .`)، مش تخمين.
- `useSearchParams()` محتاج `<Suspense>` boundary عشان الـ static prerendering ينجح في `next build` — لاحظناها لما الـ build فشل على `/login`.

## shadcn/ui بدون شبكة

`ui.shadcn.com` محجوب بسياسة الشبكة في بيئة التطوير اللي اتبنى فيها المشروع ده (403 على CONNECT). المكوّنات في `src/components/ui/` اتكتبت يدوياً (مطابقة لمصدر shadcn المعروف: `button`, `input`, `label`, `card`) بدل ما نعتمد على `shadcn init`/`shadcn add` اللي بيكلموا الشبكة دي. لو الشبكة اتفتحت مستقبلاً، تقدر تستخدم `npx shadcn@latest add <component>` عادي — بس تأكد إنه مش هيكتب فوق الملفات دي بتنسيق مختلف.

## التشغيل محلياً

```bash
# من جذر المستودع (npm workspaces) — لازم apps/api شغال على :3000 (Postgres+Redis شغالين)
npm install
cd apps/admin
cp .env.example .env.local   # لو مش موجود
npm run dev                  # بيشتغل على :3001 (مش :3000 عشان apps/api واخده)
```

`@baytak/shared-types` (`packages/shared-types`) لازم يتبني (`npm run build` هناك) بعد أي تعديل فيه قبل ما `apps/admin` يشوف الأنواع الجديدة — مفيش watch mode تلقائي دلوقتي (فجوة صغيرة، محتاجة إما TypeScript project references أو سكريبت watch لما نلاحظ الاحتكاك ده بيبطّئنا فعلاً).
