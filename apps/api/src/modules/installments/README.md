# Installments Module — محرك التقسيط (migration 0177)

التقسيط **مش نظام دفع منفصل** — امتداد للـPayment Engine الموجود بنفس المعمارية بالحرف:
- التحصيل عبر `PaymentProvider.chargeToken` (نفس مسار شغل إضافي معتمد — MOTO بوسيلة محفوظة).
- التأكيد النهائي عبر نفس webhook pipeline (`finalizeGatewayWebhook` فرع `payment.installment_id`).
- الـidempotency: مفتاح `installment:{id}:{attempt}` unique على payments + claim بـSKIP LOCKED.
- الجدولة دورة حياة منفصلة تمامًا عن دورة الطلب: طلب ممكن يكتمل وأقساطه مستمرة (حسب سياسة الخدمة).

## القرارات المعمارية الموثقة

1. **المراجعة البشرية إجبارية**: `requires_admin_approval` معماريًا دايمًا true في v1 —
   مفيش أي مسار موافقة ذاتية. الاعتماد بصلاحية `installments.review` + step-up MFA،
   والاعتماد المتزامن من أدمنين = أول واحد يكسب والتاني 409.
2. **الحساب authoritative من الباك-إند**: العميل مايبعتش أي مبلغ — `computeInstallmentBreakdown`
   (نقية، مختبرة بمصفوفة 12 حالة) بتنتج breakdown والثابت الحاكم
   `مقدم + sum(أقساط) === إجمالي ممول` مفروض قبل أي كتابة (`assertBreakdownInvariant`).
   القسط الأخير بيستوعب فرق التقريب بالكامل (floor للمنتظم).
3. **Snapshot غير قابل للتعديل**: كل الأرقام بتتخزن على الapplication وقت التقديم — تغيير
   الخطة بعدين prospective فقط. ممنوع تعديل snapshot تاريخي.
4. **التحصيل التلقائي مطفي افتراضيًا** (`installments.auto_collection_enabled=false`) — لا
   يُفعّل إلا بعد التحقق الفعلي من قدرة البوابة على merchant-initiated recurring charges ضد
   حساب Paymob حقيقي (توكنيزيشن الكارت-save webhook نفسه لسه محتاج تأكيد sandbox — راجع
   payments/README.md). مطفي = الأقساط مجدولة مرئية (BLOCKED عمليًا)، صفر سلوك مفبرك.
5. **النموذج المالي — مخاطرة المنصة (v1)**: مستحق العميل (receivable) بيتتبع في
   installments/payments، وتسوية الفني فاضلة زي ما هي على مستوى الطلب (settleAndComplete).
   يعني المنصة بتتحمل مخاطرة التحصيل. **الدفتر (wallet ledger) مابيتلمش عند تحصيل الأقساط** —
   نفس نمط دفعات الكارت اليوم (حركة المحافظ بتحصل بس عند تسوية الفني). لو الأعمال قررت نموذج
   "طرف تمويل يسوّي مقدّمًا" ده قرار منفصل هيحتاج إضافة entitlement tracking.
6. **الفشل**: كل محاولة فاشلة بتسجل last_error + attempt_count؛ retry تلقائي كل
   `installments.retry_backoff_days` (3) لحد `installments.max_auto_attempts` (3) — بعدها
   overdue مرئي للتدخل اليدوي. مفيش غرامات/إجراءات تحصيل قانونية تلقائية (قرار legal منفصل).

## الصلاحيات

| Permission | الاستخدام |
|---|---|
| `installments.view` | قراءة الطلبات/الجدولة/المستندات (finance افتراضيًا) |
| `installments.review` | اعتماد/رفض + فتح المستندات الحساسة (+step-up) |
| `installments.manage` | إدارة الخطط والربط بالخدمات |
| `payment_policies.manage` | سياسات الدفع ونشر النسخ |

## الأمان

- مستندات KYC: storage keys خاصة + MIME allowlist + magic bytes + رابط مؤقت لحظي + audit
  لكل فتح (`installment_document.viewed`). مش متاحة لأي فني/شركة/أدمن بدون `installments.review`.
- ممنوع تخزين PAN/CVV — بس provider token + masked_pan + brand (جدول payment_methods الموجود).
- DTOs ما بترجعش tokens أو أسرار بوابة أبداً.

## خارج نطاق v1 (قرارات معلقة)

- شحن تلقائي فعلي بحاجة اعتماد Paymob recurring حقيقي (فوق).
- واجهة Flutter للتقسيط (الـAPI جاهز — customer-web متغطي).
- واجهة أدمن كاملة لسياسات الدفع (الـAPI كامل — CRUD + نسخ).
- جدولة تذكير "القسط الجاي" (upcoming reminder) — محتاج قرار cadence من الأعمال.

## تدفق الاستخدام (2026-08-24)

### الأدمن
1. **إنشاء خطة**: صفحة التقسيط → تبويب "الخطط والخدمات" → "إنشاء خطة جديدة"
   - اسم، عدد أقساط، فاصل أيام، نسبة تمويل، نسبة مقدم، حد أدنى/أقصى
   - مستندات مطلوبة (مثلاً: صورة البطاقة)
2. **ربط بخدمة**: اضغط على الخطة في الجدول → اختار خدمة من الـdropdown → ربط
3. العميل هيشوف الخطة تلقائيًا عند حجز نفس الخدمة

### العميل
1. يحجز عادي من التطبيق أو الويب
2. في صفحة تفاصيل الطلب: قسم "ادفع بالتقسيط" يظهر تلقائياً لو الخدمة عليها خطط
3. يختار خطة → يوافق على الشروط → يقدم
4. الطلب بيوصل للأدمن للمراجعة (مفيش موافقة ذاتية)
5. بعد الموافقة، الجدولة بتتنشأ والعميل يشوف أقساطه في "الحجوزات المتكررة" أو تفاصيل الطلب
