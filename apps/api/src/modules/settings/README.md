# modules/settings

محرك إعدادات النظام — العمولة، الضرائب، الحد الأدنى للطلب، سياسات الإلغاء، حدود الصرف، ... من غير أي تعديل كود. جدول: `settings` (قاموس §11.2، من `infra/migrations/0011` — 12 إعداد مزروعين من اليوم الأول).

**الحالة: شغال، وموصول فعلياً بمستهلك حقيقي (مش مجرد CRUD شكلي).**

- **موديول خفيف مستقل** زي `audit`/`admin` بالظبط — عشان أي موديول تاني (`payments`, `matching`, `orders`, ...) يقرا إعداد بدون ما يعتمد على `admin`.
- **`SettingsService.getNumber/getBoolean/getString(key, fallback)`**: الطريقة الصح لأي موديول يستخدم إعداد بدل ثابت مكتوب في الكود — لو الإعداد مش موجود لأي سبب (قبل الـ seed مثلاً) بيرجع الـ fallback بدل ما ينهار.
- **`GET /admin/settings?group=`**, **`GET /admin/settings/:key`**: مفتوحة لأي أدمن (قراءة مش حساسة).
- **`PATCH /admin/settings/:key`**: محتاجة صلاحية `settings.manage` (`infra/migrations/0023` — `super_admin` بس). بيتحقق إن القيمة الجديدة نوعها مطابق لـ `value_type` بتاع الإعداد (`number`/`boolean`/`string`/`json`) قبل الحفظ — تغيير `payouts.min_amount_cents` لنص مثلاً بيترفض فوراً.
- **مُستهلك حقيقي مُثبَت**: `PayoutsService` بقى بيقرا `payouts.min_amount_cents` و`payouts.auto_approve_limit_cents` من `SettingsService` فعلياً بدل الثوابت اللي كانت مكتوبة في الكود (كان فيها تعليق صريح بينص على كده من وقت S7). القيم القديمة اتحطت كـ fallback بس، مش المصدر الحقيقي.
- **اتعمله اختبار end-to-end فعلي حاسم**: فني طلب صرف 250 جنيه ونجح تحت الحد الأدنى الافتراضي (200 جنيه) واتوافق عليه أوتوماتيك (تحت حد الموافقة التلقائية 1000 جنيه). الأدمن غيّر الحد الأدنى لـ300 جنيه عبر الـ API **من غير أي تعديل كود ولا إعادة تشغيل**، ونفس الفني حاول يطلب صرف 250 جنيه تاني فاترفض فوراً برسالة الحد الجديد بالظبط. رجّع الأدمن الحد لـ200 والطلب نجح تاني — إثبات مباشر إن التغيير حي مش cache قديم. تغيير نوع القيمة غلط (نص بدل رقم) اترفض بوضوح، تعديل إعداد مش موجود اترفض، `ops_manager` (مالوش `settings.manage`) اترفض من التعديل لكن قدر يشوف القائمة عادي، وكل تعديل اتسجّل في سجل التدقيق بالقيمة قبل وبعد بالظبط.
- **كاش Redis (S10، نقطة 12)** — كان قرار واعي إنه مؤجل ("إضافة طبيعية لما الحمل يستدعي")، دلوقتي اتوصّل: `getNumber/getBoolean/getString` بقوا كاش-أول (`RedisCacheService`, `common/cache/`) بـ TTL دفاعي 60 ثانية، مع **إبطال فوري** في `update()` — تغيير عبر الـ API بيظهر في القراءة الجاية على طول، مش بعد انتهاء الـ TTL. `getOrThrow`/`list` (مسارات الأدمن، حمل قليل) لسه بتقرا من القاعدة مباشرة عمداً.
  - **مبدأ التصميم الحاكم**: الكاش مش مصدر الحقيقة أبداً — أي فشل (Redis واقع، انقطاع شبكة) بيتلقّط ويترجع كـ cache miss عادي، القاعدة تفضل تشتغل لوحدها من غير أي كسر. اتعمله اختبار حاسم: قفل Redis فعلياً (`shutdown nosave`) والنظام كمّل يشتغل صح (قراءة/تعديل إعدادات، طلب صرف) مع تحذيرات واضحة في اللوج، وترقية الحد الأدنى وقت التوقف اتطبّقت صح من القاعدة مباشرة. **باگ حقيقي اتلقط واتصلح وقت الاختبار الحي**: أول نسخة استخدمت `retryStrategy: () => null` (تعطيل إعادة الاتصال كليةً) عشان الأوامر تفشل بسرعة — بس ده كان بيمنع العميل يرجع يتصل تاني حتى بعد ما Redis يرجع شغال (الكاش كان هيفضل ميت للأبد لحد ما الـ process يعيد تشغيل). اتصلح بفصل الاثنين: `maxRetriesPerRequest: 1` (الأمر نفسه بيفشل بسرعة، الطلب الحقيقي ميستناش) + `retryStrategy` بيحاول يعيد الاتصال في الخلفية بـ backoff. اتأكد الإصلاح حياً: رجّعت Redis بعد التوقف، وأول قراءة تالية ملّت الكاش تاني من غير أي restart للتطبيق.
- **`MatchingService` اتوصّل كمان — كانت فجوة موثّقة، اتقفلت جزئياً**: `matching.batch_size`، `matching.response_timeout_seconds`، و`matching.max_rounds` بقوا بيتقروا من `SettingsService` فعلياً (كانوا ثوابت `BATCH_SIZE`/`RESPONSE_TIMEOUT_SECONDS`/`MAX_ROUNDS` مكتوبة في `matching.service.ts` بتعليق صريح من زمان بيقول "لما لوحة الإدارة تتبني هتتقرأ من هنا" — اللوحة اتبنت). القيم القديمة بقت fallback بس. **اتعمله اختبار حي حاسم مطابق لنمط `payouts`**: غيّرت `matching.response_timeout_seconds` لـ3 ثواني عبر الـ API من غير أي restart، طلب حقيقي جديد اتعمله عبر `POST /orders` لعميل حقيقي، `order_assignments.expires_at` طابق `sent_at + 3 ثواني` بالظبط (مش 30 الافتراضية) — اتأكد بـ`psql` مباشر. بعد 3 ثواني الطلب اتلغى أوتوماتيك فعلاً (`cancelled_by_system`، مفيش فني تاني في النطاق) — إثبات إن الـ BullMQ delayed job اتجدول بالقيمة الجديدة الصح مش القديمة. رجّعت الإعداد لـ30 بعدها.
- **`orders.auto_cancel_after_minutes` — كانت فجوة موثّقة ("مزروع بس مش مستخدم")، اتقفلت**: تفاصيل الميزة الكاملة (فحص دوري مستقل عن BullMQ، السبب، والاختبار الحي) في `../orders/README.md`.
- **`orders.cancellation_free_window_min` — كانت فجوة موثّقة، اتقفلت**: منطق رسوم الإلغاء حسب نافذة زمنية (`cancellation_reasons` + `cancellation_fee_cents`) اتبنى بالكامل — تفاصيل كاملة والاختبار الحي في `../orders/README.md`.

- **بيانات تواصل خدمة العملاء (docs/08 §22 بند 15-19) — كانت فجوة موثّقة صراحة، اتقفلت بصفر جدول جديد**: `migration 0106` بتزرع 5 إعدادات `support.*` (`enabled`, `phone_number`, `whatsapp_number`, `email`, `help_url`, كلهم `group_name='support'`, `is_public=true`) — التعديل عبر `PATCH /admin/settings/:key` الموجود بالفعل (`settings.manage` + MFA step-up + audit، صفر كود إضافي). `SupportContactController` (`@Public() GET /settings/support-contact`، نفس فلسفة `BrandingController`) بيعمل التحقق الأمني لـ deep link (whatsapp أرقام بس، `help_url` لازم `https://`) قبل ما يرجّعهم للتطبيقات — تفاصيل كاملة في `support-contact.controller.ts` و`support-contact.controller.spec.ts`. **تحديث (2026-08-22)**: `apps/customer-web` بقى بيستهلك نفس الـendpoint في الصفحة الرئيسية (كان بيستخدمه Flutter بس قبل كده) — صفر تعديل باك-إند.
- **محتوى الصفحة الرئيسية لـ`apps/customer-web` (طلب مالك مباشر 2026-08-22)** — نفس نمط `support.*` بالحرف: `migration 0174` بتزرع `homepage.trust_message` (`string`, `group_name='homepage'`, `is_public=true`, قيمة افتراضية حقيقية مش فاضية). `HomepageContentController` (`@Public() GET /settings/homepage-content`) بيرجّعها كما هي (مفيش تحقق أمان زي whatsapp/help_url — نص عرض بس، صفر deep link). التعديل عبر `PATCH /admin/settings/:key` الموجود، هيظهر تلقائيًا في `apps/admin/src/app/settings` (الشاشة عامة بالكامل، صفر UI مخصّص لازم).

- **`SETTING_UPDATED_EVENT` (`common/events/setting-updated.event.ts`) — بدائي جديد لموديولات محتفظة بقيمة إعداد في الذاكرة (docs/08 §33، طلب مالك صريح 2026-08-20)**: كل الأمثلة فوق (payouts، matching، orders) بتقرا `SettingsService.getX()` **في كل نداء** — كافي تمامًا، مفيش داعي لحدث. بس لو موديول عنده `@Injectable()` singleton بيحتفظ بقيمة الإعداد كـ`readonly`/field محسوب مرة واحدة وقت `bootstrap` (زي `InstaPayProvider.isConfigured` — راجع `../payments/README.md` §33)، `update()` بقى بتطلق `SETTING_UPDATED_EVENT` (`emitAsync`، بعد إبطال الكاش مباشرة) — أي موديول يستمع له بـ`@OnEvent(SETTING_UPDATED_EVENT)` ويتحقق `event.key` قبل ما يعيد تحميل قيمته. **قيد نطاق صريح**: `EventEmitter2` in-process بس — لو النظام يوماً بقى multi-instance، الحدث مش هيوصل لباقي الـinstances، لازم يتحول لـRedis pub/sub. `events: EventEmitter2` بقى param **اختياري** في `SettingsService`'s constructor (24+ ملف اختبار بينشئوها بـ`new` بـ3 args بس، إجباره كان هيكسرهم كلهم).
