# modules/settings

محرك إعدادات النظام — العمولة، الضرائب، الحد الأدنى للطلب، سياسات الإلغاء، حدود الصرف، ... من غير أي تعديل كود. جدول: `settings` (قاموس §11.2، من `infra/migrations/0011` — 12 إعداد مزروعين من اليوم الأول).

**الحالة: شغال، وموصول فعلياً بمستهلك حقيقي (مش مجرد CRUD شكلي).**

- **موديول خفيف مستقل** زي `audit`/`admin` بالظبط — عشان أي موديول تاني (`payments`, `matching`, `orders`, ...) يقرا إعداد بدون ما يعتمد على `admin`.
- **`SettingsService.getNumber/getBoolean/getString(key, fallback)`**: الطريقة الصح لأي موديول يستخدم إعداد بدل ثابت مكتوب في الكود — لو الإعداد مش موجود لأي سبب (قبل الـ seed مثلاً) بيرجع الـ fallback بدل ما ينهار.
- **`GET /admin/settings?group=`**, **`GET /admin/settings/:key`**: مفتوحة لأي أدمن (قراءة مش حساسة).
- **`PATCH /admin/settings/:key`**: محتاجة صلاحية `settings.manage` (`infra/migrations/0023` — `super_admin` بس). بيتحقق إن القيمة الجديدة نوعها مطابق لـ `value_type` بتاع الإعداد (`number`/`boolean`/`string`/`json`) قبل الحفظ — تغيير `payouts.min_amount_cents` لنص مثلاً بيترفض فوراً.
- **مُستهلك حقيقي مُثبَت**: `PayoutsService` بقى بيقرا `payouts.min_amount_cents` و`payouts.auto_approve_limit_cents` من `SettingsService` فعلياً بدل الثوابت اللي كانت مكتوبة في الكود (كان فيها تعليق صريح بينص على كده من وقت S7). القيم القديمة اتحطت كـ fallback بس، مش المصدر الحقيقي.
- **اتعمله اختبار end-to-end فعلي حاسم**: فني طلب صرف 250 جنيه ونجح تحت الحد الأدنى الافتراضي (200 جنيه) واتوافق عليه أوتوماتيك (تحت حد الموافقة التلقائية 1000 جنيه). الأدمن غيّر الحد الأدنى لـ300 جنيه عبر الـ API **من غير أي تعديل كود ولا إعادة تشغيل**، ونفس الفني حاول يطلب صرف 250 جنيه تاني فاترفض فوراً برسالة الحد الجديد بالظبط. رجّع الأدمن الحد لـ200 والطلب نجح تاني — إثبات مباشر إن التغيير حي مش cache قديم. تغيير نوع القيمة غلط (نص بدل رقم) اترفض بوضوح، تعديل إعداد مش موجود اترفض، `ops_manager` (مالوش `settings.manage`) اترفض من التعديل لكن قدر يشوف القائمة عادي، وكل تعديل اتسجّل في سجل التدقيق بالقيمة قبل وبعد بالظبط.
- **كاش Redis (S10، نقطة 12)** — كان قرار واعي إنه مؤجل ("إضافة طبيعية لما الحمل يستدعي")، دلوقتي اتوصّل: `getNumber/getBoolean/getString` بقوا كاش-أول (`RedisCacheService`, `common/cache/`) بـ TTL دفاعي 60 ثانية، مع **إبطال فوري** في `update()` — تغيير عبر الـ API بيظهر في القراءة الجاية على طول، مش بعد انتهاء الـ TTL. `getOrThrow`/`list` (مسارات الأدمن، حمل قليل) لسه بتقرا من القاعدة مباشرة عمداً.
  - **مبدأ التصميم الحاكم**: الكاش مش مصدر الحقيقة أبداً — أي فشل (Redis واقع، انقطاع شبكة) بيتلقّط ويترجع كـ cache miss عادي، القاعدة تفضل تشتغل لوحدها من غير أي كسر. اتعمله اختبار حاسم: قفل Redis فعلياً (`shutdown nosave`) والنظام كمّل يشتغل صح (قراءة/تعديل إعدادات، طلب صرف) مع تحذيرات واضحة في اللوج، وترقية الحد الأدنى وقت التوقف اتطبّقت صح من القاعدة مباشرة. **باگ حقيقي اتلقط واتصلح وقت الاختبار الحي**: أول نسخة استخدمت `retryStrategy: () => null` (تعطيل إعادة الاتصال كليةً) عشان الأوامر تفشل بسرعة — بس ده كان بيمنع العميل يرجع يتصل تاني حتى بعد ما Redis يرجع شغال (الكاش كان هيفضل ميت للأبد لحد ما الـ process يعيد تشغيل). اتصلح بفصل الاثنين: `maxRetriesPerRequest: 1` (الأمر نفسه بيفشل بسرعة، الطلب الحقيقي ميستناش) + `retryStrategy` بيحاول يعيد الاتصال في الخلفية بـ backoff. اتأكد الإصلاح حياً: رجّعت Redis بعد التوقف، وأول قراءة تالية ملّت الكاش تاني من غير أي restart للتطبيق.
- **فجوة موثّقة**: باقي الموديولات (`matching`, `orders` cancellation policy, ...) لسه بتستخدم ثوابتها المكتوبة في الكود بدل `SettingsService` — `payouts` بس اتوصّل كمثال حقيقي مُثبَت، والباقي نفس النمط لما يتاح الوقت.
