# apps/api — NestJS Backend

الـ Backend الأساسي (Modular Monolith). كل موديول جوّه `src/modules/*` وله حدود مستقلة (راجع §2.4 في الماستر بلان).

الستاك: NestJS + PostgreSQL 16 + PostGIS + Redis (لسه) + TypeORM (query layer بس — الـ schema مصدره `infra/migrations` الوحيد، `synchronize: false` دايماً).

## الحالة

**موديول `auth` كامل وشغال (S1 من المرحلة 1 — MVP):**

- تسجيل ودخول برقم موبايل + OTP (`otp_codes` مُشفّرة بـ bcrypt، 5 محاولات كحد أقصى)
- JWT access token (15 دقيقة) + refresh token بتدوير كامل (كل استخدام يبطّل القديم، وإعادة استخدام توكن مُلغى تقفل كل توكنات المستخدم فوراً)
- RBAC على مستوى `user_type` عبر `@Roles()` + `RolesGuard`، وكل الـ endpoints محمية افتراضياً إلا اللي معلّم عليها `@Public()`
- Rate limiting: 60 طلب/دقيقة عام، 5/دقيقة على `POST /auth/otp/request`
- عقد استجابة موحّد `{success, data, meta, error, request_id}` عبر `ResponseInterceptor` + `AllExceptionsFilter`، وأكواد الأخطاء مطابقة لـ `docs/02-data-dictionary.md` §13.9
- اختبار end-to-end فعلي تم على قاعدة بيانات PostgreSQL+PostGIS حقيقية (مش mock) — كل الـ endpoints شغالة ومطابقة للعقد المُوثّق

**موديولات `geo`, `customers`, `technicians`, `catalog` شغالة جزئياً (S2):**

- `geo`: `GET /cities`, `GET /cities/:id/areas` (قراءة بس)
- `customers`: `customer_profiles` بتتعمل تلقائياً وقت التسجيل (حدث `user.registered` — لا استدعاء مباشر من `auth`)، و CRUD كامل على `/addresses` مع التحقق من تغطية المنطقة
- `technicians`: `technician_profiles` بتتعمل تلقائياً برضه، مع `technician_code` مولّد من DB sequence، و`GET /technician/me`, `GET /technician/level` محميين بـ RBAC
- `catalog`: `GET /service-categories`, `GET /services`, `GET /services/:id`, `POST /services/:id/estimate`

كل ده اتعمله اختبار end-to-end فعلي: تسجيل عميل/فني حقيقي → إنشاء بروفايل تلقائي → عنوان في منطقة مُطلقة (نجح) وفي منطقة مش مُطلقة (اترفض بالكود الصح ORDR_001) → تسعير تقديري لخدمة حقيقية → RBAC بيمنع عميل من مسارات الفني (403).

**موديول `orders` شغال (S3 + S5 + S6) — الإنشاء، الإلغاء، دورة عمل الفني، والتتبع اللحظي:**

- `order-state-machine.ts`: state machine مقفولة كاملة (كل الـ 18 حالة من القاموس §6.2) — انتقال مش معرّف = `ORDR_003`.
- `POST /orders`: يتحقق من ملكية العنوان، الخدمة، نطاق التغطية، يحسب السعر التقديري، ويولّد `order_number` تسلسلي — كل ده جوّه transaction واحدة مع أول صف تاريخ حالة.
- `POST /orders/:id/cancel`: بيحترم الـ state machine، وبيرفض إلغاء طلب اتلغى قبل كده.
- `POST /technician/orders/:id/depart|arrive|start|complete` (S5): دورة عمل الفني بعد القبول، كل خطوة بتتحقق من ملكية الطلب والانتقال المسموح.
- `POST /technician/orders/:id/media` (S5): رفع صور قبل/بعد فعلي (multipart)، وراه واجهة `StorageService` قابلة للتبديل لـ S3 في الإنتاج.
- `OrderTrackingGateway` (S6, WebSocket `/tracking`): موقع الفني بيتبعت لحظياً للعميل، بس أثناء الطلب فعّال، ويوقف تلقائي بعد الاكتمال.
- اتعمله اختبار end-to-end فعلي كامل: إنشاء طلب → قبول فني → المسار الكامل depart→arrive→start (مع رفض محاولة `complete` قبل الأوان) → رفع صورة PNG حقيقية اتكتبت على القرص فعلاً → complete → تاريخ حالات كامل (7 خطوات) مطابق للقاموس → موقع الفني اتبعت WebSocket ووصل للعميل فوراً.

**موديول `matching` شغال (S4) — توزيع الطلبات على الفنيين:**

- بيبعت الطلب أوتوماتيك لأقرب 5 فنيين مؤهلين (استعلام PostGIS حقيقي بالمسافة) لحظة الإنشاء، وبيعيد المحاولة لجولة جديدة لو الكل رفض، وبيلغي الطلب أوتوماتيك (`ORDR_002`) لو مفيش فنيين خالص.
- **أول واحد يقبل ياخده** — مضمون بقفل ذري حقيقي (`SELECT ... FOR UPDATE`) مش مجرد افتراض.
- **اتعمله اختبار concurrency فعلي**: 5 فنيين حقيقيين حاولوا يقبلوا نفس الطلب بالتوازي (background processes مش تسلسلي) — واحد بس فاز، الباقي اترفضوا بأمان بالكود الصح، صفر تعيين مزدوج. الاختبار ده كشف bug حقيقي (الطلب كان بيعلق لو الرفض حصل بعد الجولة الأولى) واتصلح فوراً.

**موديول `chat` شغال (S6) — المحادثة بين العميل والفني:**

- خيط شات بيتعمل تلقائياً لما الفني يقبل الطلب (حدث `order.accepted`)، مع WebSocket فعلي (namespace `/chat`) وREST fallback.
- كشف عملي لمحاولات تبادل أرقام موبايل (`is_flagged`) — بيعلّم الرسالة مش بيرفضها.
- **اتعمله اختبار end-to-end فعلي بعميلين WebSocket حقيقيين**: رسالة عادية وصلت للطرفين فوراً وهي `is_flagged:false`، رسالة فيها رقم موبايل مصري وصلت وهي `is_flagged:true`، وطرف تالت اترفض بـ 403 لما حاول يدخل خيط مش بتاعه.

**موديول `payments` شغال (S7) — كاش، محفظة، صرف الفنيين، استرجاع (Paymob لسه):**

- محرك دفتر مزدوج ذرّي (`WalletsService.doubleEntry`) — بيقفل المحفظتين بترتيب ثابت يمنع الـ deadlock، وبيشارك في transaction الطالب بدل ما يفتح واحدة لوحده.
- تسوية عمولة تلقائية عند تحصيل الكاش أو الدفع بالمحفظة، حجز رصيد ذرّي للصرف (`reserveForPayout`)، وموافقة تلقائية/يدوية حسب سقف المبلغ.
- **مراجعة داخلية صارمة قبل الاختبار كشفت وصلحت بَقّتين ماليتين حقيقيتين** قبل ما توصل للفرع: (1) محفظة مش موجودة كانت ممكن تتطابق غلط مع محفظة تانية موجودة بصمت من غير error، (2) استرجاع الكاش كان بيرجّع أرباح الفني بس من غير ما يعوّض العميل فعلياً رغم إنه بيقول `refundMethod=wallet_credit`.
- **اتعمله اختبار end-to-end شامل جداً**: دورة كاش كاملة بتسوية عمولة صحيحة 100%، استرجاع بيرجّع الدفتر لصفر بالظبط (اتحقق منه رياضياً)، رفض دفع مكرر ورصيد غير كافٍ ومفتاح idempotency مكرر، ورفض صرف تحت الحد الأدنى وفوق الرصيد — وأهم حاجة: **3 طلبات صرف متزامنة فعلياً على رصيد يكفي واحد بس، واحد نجح فقط والباقي اترفضوا بأمان، مجموع كل المحافظ فضل صفر طول الوقت**.
- ~~لسه من غير: بوابة Paymob/Fawry الحقيقية (محتاجة إنترنت خارجي مش متاح هنا)~~ — **اتقفلت لاحقاً**: تكامل Paymob Accept API v1 كامل (auth → order → payment key → iframe، webhook بتحقق HMAC-SHA512 حقيقي)، مبني معمارياً بالكامل بـ placeholders للمفاتيح (نمط `isConfigured` زي كل تكامل خارجي تاني في المشروع) — تفاصيل كاملة في `payments/README.md` و`docs/03-external-integrations.md`.

**موديولات `ratings` و `support` شغالة (S8) — التقييم والشكاوى:**

- `ratings`: تقييم واحد بس لكل طلب (مطابق للـ `UNIQUE` في القاموس الأصلي حرفياً) — أول طرف يقيّم ياخد السلوت.
- `support`: شكاوى بحالات مقفولة (`open→under_investigation→resolved/rejected→closed`)، تعويض حقيقي بيتحوّل لمحفظة صاحب الشكوى وقت الحل (مش مجرد رقم في العمود)، وملاحظات داخلية مخفية عن العميل/الفني تماماً.
- **بَقّة RBAC حقيقية اتكشفت واتصلحت أثناء الاختبار**: فريق الدعم (أدمن) كان مقفول برّه مسارات قراءة/رد الشكاوى بالكامل بسبب `@Roles` على مستوى الكلاس بس — يعني محدش من الإدارة كان يقدر يرد على شكوى. اتصلحت بإضافة `@Roles` على مستوى كل method محتاج صلاحية أوسع.
- اتعمله اختبار end-to-end شامل: شكوى اتفتحت وربطت أوتوماتيك بالطرف التاني، تعويض 20 جنيه اتحوّل فعلياً واتأكد من رصيد المحفظة قبل/بعد، حل شكوى مرتين اترفض، ملاحظة داخلية اتخبت عن العميل، وقفل شكوى قبل حلها اترفض.
- **فجوة كانت موثّقة هنا اتقفلت لاحقاً**: الأدوار الإدارية الدقيقة بقت مفعّلة فعلياً عبر `PermissionsGuard` — تفاصيل كاملة في `admin/README.md`.

**موديول `notifications` شغال (دعم بنية تحتية عبر الموديولات) — الإشعارات وأجهزة المستخدمين:**

- `POST/DELETE /devices`: تسجيل/إلغاء جهاز، مع نقل ملكية تلقائي لو نفس `device_id` اتسجّل بحساب تاني (خروج/دخول بحساب مختلف على نفس الموبايل)، و"غير موجود" موحّدة لجهاز مش موجود أو مش بتاعك (مفيش تسريب معلومة).
- بوابة إرسال قابلة للتبديل (`NotificationDispatcher`، نفس فلسفة `StorageService`) — التنفيذ الحالي بيسجّل في اللوج ويتحقق فعلياً من وجود target (fcm token / رقم / بريد) قبل ما يعتبر أي قناة غير `in_app` ناجحة؛ مفيش بوابة FCM/SMS/SMTP حقيقية لسه (نفس حالة OTP في `auth`، موثّق صراحة).
- حدث جديد `order.status_changed` اتضاف في `orders.service.ts` (بيتصدر من نفس نقطة انتقال حالة الفني ونقطة إلغاء العميل) — أي موديول تاني يقدر يشترك فيه من غير ما يعرف تفاصيل الـ state machine.
- استماع تلقائي كامل لأحداث `user.registered`, `order.created`, `order.accepted`, `order.status_changed` — إشعار ترحيب، إشعار إنشاء الطلب للعميل، إشعار قبول للعميل والفني الاتنين، وإشعارات دورة العمل (في الطريق/وصل/بدأ/خلص) للعميل + إشعار إلغاء للفني.
- اتعمله اختبار end-to-end فعلي شامل: دورة طلب كاملة بكل إشعاراتها بالترتيب الصح لطرفين حقيقيين، نقل ملكية جهاز فعلي بين حسابين، فشل واضح لقناة `push` من غير جهاز فعّال ونجاح فعلي مع `fcm_token`، و`mark-all-read`/`unread-count` اتأكد منهم.
- ~~فجوة موثّقة: إشعارات الدفع والشكاوى والتقييمات لسه مش متغطية~~ — **اتقفلت لاحقاً**: `rating.submitted` (إشعار مباشر لصاحب التقييم)، `complaint.filed`/`payout.requires_review` (توجيه حسب الدور)، و`order.status_changed` بقى بيغطي اكتمال الدفع (`WORK_COMPLETED`/`completed`) كمان — تفاصيل كاملة في `notifications/README.md`. بوابات إرسال حقيقية (FCM/Twilio SMS+WhatsApp/SMTP) اتبنت معمارياً بعد كده بـ placeholders — نفس README.

**S9 (لوحة الإدارة) — اعتماد الفنيين + متابعة الطلبات لحظياً:**

- **اعتماد الفنيين** (`technicians`): الفني بيرفع مستنداته (`POST/GET /technician/documents`، multipart)، والأدمن (`/admin/technicians`) بيراجع، يوافق، أو يرفض — مستند واحد أو الفني كله، مع سبب إلزامي للرفض.
  - **بَقّة حقيقية اتصلحت قبل الاختبار**: أول نسخة من `technician-verification-state-machine.ts` كانت بتطلب `pending→under_review` قبل `approved`، بس مفيش endpoint أصلاً ينقل لـ `under_review` — يعني فني جديد ماكانش هيتوافق عليه أبداً عبر الـ API. اتصلحت بالسماح لـ `approved`/`rejected` من أي حالة وسيطة.
- **متابعة الطلبات + تدخل يدوي** (`orders`): `/admin/orders` — قائمة مفلترة بالحالة وفترة زمنية، تفاصيل مع تاريخ الحالات الكامل، إلغاء إداري (سبب إلزامي، بيحترم الـ state machine فمينفعش بعد قبول الفني)، وتعيين فني معتمد مباشرة (`reassign`).
  - **بَقّة حقيقية تانية اتصلحت قبل الاختبار**: أول نسخة من `reassign` كانت بتسيب الطلب `technician_assigned` والفني "يقبل" بنفسه — لكن مسار القبول العادي بيرفض أي طلب مش `searching_technician` أصلاً، فالفني المُعيَّن يدوياً ماكانش هيقدر يتحرك بالطلب خالص. اتصلحت بخلي `reassign` يعدّي بنفس انتقالي الـ state machine (`searching_technician→technician_assigned→accepted`) في transaction واحدة.
- حدثين جديدين وصلوا لـ `notifications`: `technician.verification_changed` (موافقة/رفض الفني بسبب واضح) و `order.reassigned` (الفني المُعيَّن يدوياً بياخد إشعار فوري)، وحدث `order.status_changed` الموجود بقى بيغطي الإلغاء الإداري كمان (الطرفين الاتنين).
- اتعمله اختبار end-to-end فعلي شامل لكل ده (تفاصيل في `technicians/README.md` و `orders/README.md`)، بما فيه منع عميل من كل مسارات الأدمن (403).
- **التقارير** (`admin`، موديول جديد): `GET /admin/dashboard/stats` (طلبات النهاردة، إيراد وعمولة النهاردة، حالة الفنيين، شكاوى مفتوحة، متوسط التقييم) و `GET /admin/reports/revenue?from=&to=&group_by=` (تجميع حقيقي من `orders.paid_at` بـ `date_trunc`). اتعمله اختبار فعلي بدورة كاش كاملة والأرقام طابقت القاعدة بالظبط (تفاصيل في `admin/README.md`).
- ~~فجوة موثّقة: القاموس §13.7 بيعرّف endpoints تانية كتير تحت /admin لسه مبنيتش~~ — **اتقفلت لاحقاً بالكامل تقريباً**: بلوك عملاء، تعديل سعر، تعليق فني، CRUD عروض/خدمات (كتالوج)، الإعدادات، سجل التدقيق، تقارير فنيين/مناطق، حذف موظف، مناطق عمل الفني، الحالات الوسيطة لاعتماد الفني، وأكتر — القائمة الكاملة والحالة الحقيقية في `admin/README.md` و`technicians/README.md` و`catalog/README.md`.

**موديول `promotions` شغال — أكواد الخصم والولاء:**

- كود خصم اختياري (`promo_code`) في `POST /orders` بيتحقق ويتطبّق فعلياً جوّه transaction إنشاء الطلب نفسها — كل الشروط (نشط، فترة صلاحية، حد أدنى، خدمة/منطقة، عملاء جداد بس، حد استخدام كلي وللمستخدم، ميزانية) بتتفحص حقيقي، والخصم محسوب صح لكل الأنواع التلاتة (نسبة، مبلغ ثابت، كشف مجاني) مع سقف أقصى.
- **أمان ذرّي حقيقي مُختبر**: قفل `SELECT ... FOR UPDATE` على صف الكود جوّه نفس transaction الطلب — **3 عملاء حقيقيين حاولوا يستخدموا كود بحد أقصى استخدام واحد بالتوازي فعلياً (مش تسلسلي)، واحد بس نجح، صفر تجاوز للحد، صفر طلبات يتيمة من المحاولات الفاشلة**.
- `loyalty`: دفتر نقاط بسيط (`earn`/`redeem`) بقفل ذرّي على رصيد العميل، مع `GET /loyalty/balance`, `GET /loyalty/transactions`, و`POST /admin/customers/:userId/loyalty/credit` للرصيد اليدوي.
- إدارة أدمن كاملة لأكواد الخصم (`/admin/promo-codes`: إنشاء/قائمة/تعطيل).
- **فجوة موثّقة**: مفيش قاعدة تلقائية لكسب نقاط الولاء من الطلبات — القاموس مالوش رقم محدد، فمش هختلقه (تفاصيل في `promotions/README.md`).

**الصلاحيات الإدارية الدقيقة (`PermissionsGuard`) — فجوة كانت موثّقة في أكتر من README اتقفلت:**

- جداول `roles`/`permissions`/`role_permissions`/`user_roles` (موجودة من `infra/migrations/0003` بس فاضية) اتفعّلت عبر migration جديدة (`0020_permissions_seed.sql`، مفيش تعديل على 0003 القديمة) زرعت 10 صلاحيات دقيقة ووزّعتها على الأدوار الخمسة حسب منطقها.
- `PermissionsGuard` جديد مسجّل global زي `RolesGuard` بالظبط — بيتحقق **حياً من القاعدة** (مش من التوكن) وبيتطبّق بس على الأفعال الحساسة (إلغاء طلب، تعيين فني، اعتماد فني، صرف فلوس، استرجاع، حل شكوى، إدارة عروض) مش على أي `GET`.
- `AdminUsersController` جديد لمنح/سحب الأدوار (`roles.manage`) — بوتستراب أول `super_admin` لازم SQL مباشر مرة واحدة وقت التجهيز، موثّق كقرار أمان واعي مش قصور.
- **اتعمله اختبار end-to-end فعلي شامل** بـ 4 حسابات أدمن حقيقية بأدوار مختلفة (بدون دور، `ops_manager`، `finance`، `super_admin`): كل مصفوفة الصلاحيات اتأكد منها فعلياً (مين يعدي ومين يترفض لكل فعل)، منح/سحب دور أثّر فوراً من غير أي re-login (إثبات إن الفحص حي)، وعميل اتمنع بالكامل قبل ما يوصل حتى لطبقة الصلاحيات. التفاصيل الكاملة في `admin/README.md`.

**مهلة جولة توزيع حقيقية عبر BullMQ (`matching-rounds`) — فجوة سلوكية حقيقية اتقفلت، مش بس توثيقية:**

- قبل كده: فني ماردّش خالص على عرض (لا قبول ولا رفض) كان بيسيب الطلب عالق للأبد — الجولة التالية كانت بتتبعت بس لو **كل** العروض اترفضت صراحة. دلوقتي `dispatchNextRound()` بيجدول job حقيقي مؤجّل (30 ثانية، `@nestjs/bullmq`)، و`MatchingRoundExpiryProcessor` بيقفل الجولة ويبعت التالية أوتوماتيك لو محدش رد.
- اتعمله اختبار فعلي (مش mock للوقت — استُنى 30 ثانية حقيقية): عرض اتبعت لفني واحد، محدش رد، الـ processor حوّل العرض لـ`timeout` وبعت جولة تانية، مفيش مرشحين فألغى الطلب أوتوماتيك — من غير أي تدخل بشري. اختبار تاني أثبت مفيش regression: فني قبل قبل ما المهلة تخلص، والـ job بتاعها اشتغل وقت المهلة لكن عمل no-op تام.
- **باگ حقيقي اتلقط واتصلح وقت الاختبار الحي — نفس الفجوة اللي الميزة جاية تصلحها كانت لسه موجودة في أول نسخة**: BullMQ بيرفض أي `jobId` فيه `:`، والخطأ كان بيتلقّط بصمت (بالتصميم، مايكسرش إنشاء الطلب)، يعني الـ job الحقيقي مكانش بيتزرع خالص. اتصلح واتأكد حياً. التفاصيل الكاملة في `matching/README.md`.

**إحصائيات الفني بمهمة خلفية حقيقية (`technician_profiles.completed_orders_count`/`average_rating`) — فجوة كانت موثّقة من أول يوم اتقفلت:**

- اتعمله اختبار حاسم: طلب حقيقي اكتمل ودفع → العدد اتحدّث فوراً مطابق تماماً لعدّ مباشر بالقاعدة؛ تقييمين (4 ثم 2 نجوم) → المتوسط بقى 3.00 بالظبط.
- **باگ حقيقي خطير اتلقط واتصلح**: أول نسخة كانت بتعلّق الطلب الحقيقي كله (تقييم أو دفع) لدقايق لو Redis واقع، مش بس فشل الجدولة نفسها — `queue.add()` كانت بتحجز الأمر في طابور داخلي بدل ما ترفض فوراً. اتصلح بـ`enableOfflineQueue: false` على اتصال BullMQ، واتأكد الإصلاح: نفس العملية بقت بترجع في أقل من 0.1 ثانية وقت انقطاع Redis بدل ما تعلّق.
- **فجوة موثّقة صريحة (اتعمل فيها تحقيق عميق بعد كده، لسه من غير حل)**: جانب الإرسال (enqueue) بيفشل بسرعة وأمان مؤكّد بالاختبار، لكن جانب المعالجة (Worker) مبيرجّعش يعالج وظايف جديدة بعد انقطاع طويل لـRedis — الـ job فضل قاعد بأمان في الطابور (مفيش فقدان بيانات) لحد ما الـ app اتعاد تشغيله. اتعمل تحقيق حي مكثّف بعد كده (3 محاولات إصلاح مختلفة، اتنين منهم كشفوا وصلّحوا بَقّتين حقيقيتين تانيين — راجع `technicians/README.md`) لكن السبب الجذري اتأكد إنه بَقّة موثّقة رسمياً في BullMQ نفسه (GitHub #4479)، مش حاجة تتصلح من كود التطبيق بس. التفاصيل الكاملة في `ratings/README.md` و`technicians/README.md`.

## الأمان (2026-08-13 — جولة تحصين قبل الإطلاق)

مراجعة أمنية شاملة اتعملت على كل الـ backend (مش بس أول مرة على branch معيّن)، بالإضافة لما كان
موجود أصلاً من أول يوم (`auth`/`payments`/`wallets` مبنيين بمعايير صارمة من البداية):

**كان موجود بالفعل قبل الجولة دي (اتراجع وتأكّد سليم):**
- OTP مُشفّرة بـ`bcrypt` (مش نص صريح)، حد أقصى محاولات، rate limit 5/دقيقة على `POST /auth/otp/request`.
- Refresh token: مُخزّن كـ`sha256` hash بس (مش الخام)، **يتدوّر إجباريًا مع كل استخدام**، وإعادة
  استخدام توكن سبق تدويره (سرقة محتملة) بتقفل كل توكنات المستخدم فورًا (`revokeAllUserTokens`).
- `ValidationPipe` عام: `whitelist + forbidNonWhitelisted` — أي حقل زيادة عن الـDTO يترفض 400
  (حماية من mass-assignment)، مش بس يتجاهل.
- كل استعلامات SQL مُعاملة (parameterized) عبر TypeORM QueryBuilder — صفر تركيب نصي مباشر لقيم
  مستخدم داخل استعلام (اتفحص الكود كله صراحة، صفر نتائج).
- رفع الملفات (صور طلبات/مستندات فنيين/مرفقات شكاوى): حد أقصى حجم + قائمة MIME مسموحة صراحة على
  كل endpoint، مش مجرد قبول أي حاجة.
- `envValidationSchema` (Joi) بيرفض الإقلاع من الأصل لو `DATABASE_URL`/`JWT_*` ناقصين.

**اتضاف في الجولة دي:**
- **`helmet`**: رؤوس أمان قياسية على كل response (`X-Content-Type-Options`, `X-Frame-Options`,
  `Strict-Transport-Security`, `Referrer-Policy`, إلخ). `contentSecurityPolicy` معطّلة عمداً (API
  JSON بحت من غير صفحات HTML مُصيَّرة — قيمتها الحقيقية مش موجودة هنا)، و`crossOriginResourcePolicy`
  مضبوطة صراحة على `cross-origin` عشان صور `/uploads/*` تفضل قابلة للتحميل من لوحة الأدمن/تطبيقات
  Flutter على أصل مختلف في الإنتاج.
- **CORS عبر allowlist مُعدّة بـ`CORS_ORIGIN`** (env جديد، مفصول بفاصلة) بدل `enableCors()` المفتوحة
  للكل بلا قيد. فاضي = مفتوح للكل (مقبول تطويريًا بس)، لكن **`env.validation.ts` بيرفض الإقلاع خالص
  لو `NODE_ENV=production` و`CORS_ORIGIN` فاضية** — مينفعش حد ينشر بالخطأ من غير ما يحددها. ملحوظة:
  الـJWT بيتبعت كـ`Authorization: Bearer` مش cookie، فالقيد ده دفاع إضافي (defense-in-depth) مش
  الحماية الوحيدة أصلاً.
- **رفض الأسرار الافتراضية في الإنتاج**: `JWT_ACCESS_SECRET`/`JWT_REFRESH_SECRET` في `.env.example`
  قيمتهم `change-me-*-secret` (يشتغلوا محليًا/تطويريًا عادي، نفس دليل `README.md` الرئيسي). لو
  `NODE_ENV=production`، Joi بيرفض هاتين القيمتين بالتحديد بالاسم + بيطلب طول أدنى 32 حرف (مش 16)
  + بيرفض تطابق سر access مع refresh — كل ده fail-fast وقت الإقلاع، مش اكتشاف متأخر بعد أول اختراق.
- **تصليح ثغرات تبعيات (dependencies)**: `npm audit` كشف 3 ثغرات عالية الخطورة في تبعيات إنتاجية
  فعلية (`multer` — DoS عبر استغلال parsing، `uuid` — تجاوز حدود buffer، `lodash` — code injection/
  prototype pollution عبر `_.template`/`_.unset`/`_.omit`). الإصلاح عبر `overrides` في `package.json`
  الجذر (`multer@2.2.0`, `uuid@^11.1.1`, `lodash@^4.18.1`) — **بدون** الترقية الكسّارة لـ`@nestjs/*` v11
  اللي كان `npm audit fix --force` هيعملها (تغيير جذري في 20+ موديول، خطر غير مبرر قبل إطلاق). الثغرات
  المتبقية بعد كده (`@nestjs/cli`, `glob`, `picomatch`, `tmp`) كلها في أدوات بناء تعمل وقت التطوير على
  جهاز المطوّر بس، مش في مسار تشغيل الإنتاج — قرار واعي بعدم لمسها الآن، مش سهو.

**تحقق فعلي**: السيرفر اتشغّل حي بعد كل التعديلات دي — الرؤوس ظهرت صح في الـresponse فعليًا
(`curl -D-`)، تحذير `CORS مفتوح للكل` ظهر صح في اللوج وقت التشغيل المحلي (متوقع، `CORS_ORIGIN` فاضية
في `.env` المحلي)، و`tsc --noEmit` + `nest build` + الـ42 اختبار كلهم عدّوا نضيف بعد التغيير.
