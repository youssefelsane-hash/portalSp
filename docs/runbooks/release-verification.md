# التحقق من نسخة الإصدار قبل النشر (ج-١٥)

> الفرق بين `debug` و`release` **مش تفصيلة بناء** — هو فرق في الكود اللي بيتنفّذ فعلاً. الخطوات
> هنا مكتوبة عشان **تتنفّذ**، مش تتقري.

## اللي بيتفحص آليًا (كل push)

```bash
node scripts/release-readiness-audit.js       # ١٤/١٤
```
وفي CI: `flutter analyze` + `flutter test` + `flutter build apk --debug` + **`--release`**.

`--release` هو اللي بيكشف الفئة اللي `--debug` عمياء عنها:
- **R8/tree-shaking** بيشيل كلاسات مالهاش مرجع ثابت — أي حاجة بتتنادى بالـreflection
  (Firebase، فك JSON) ممكن تختفي.
- **فروع `kDebugMode` بتتشال بالكامل** — قيمة افتراضية للتطوير ممكن تكون مغطّية عطلًا.
- **`assert()` بتتشال** — أي ثابت كان محمي بيها بيعدّي بصمت.

## اللي **لازم** يتنفّذ يدويًا على جهاز حقيقي

الفحص الآلي بيقرا الكود؛ الحاجات دي محتاجة جهاز وشبكة حقيقيين.

### ١) بناء نسخ Google Play — **بأمر واحد بس**

```bash
scripts/build-play-release.sh           # العميل + الفني ← dist/play/*.aab
scripts/build-play-release.sh all --apk # + APK للتجربة على الموبايل قبل الرفع
```

السكربت بيبني بعنوان الإنتاج، **وبيفتح الملف الناتج نفسه** ويتأكد إن العنوان متخبّز جوّه الكود
المترجم وعنوان التطوير مش موجود، وبيطبع بصمة التوقيع عشان تقارنها بمفتاح الرفع في Play Console.
**ماترفعش أي ملف مااتطلعش من السكربت ده.**

#### ليه — حادثة 1.0.7+8 (2026-09-28)

النسختين اتبنوا **من غير** `--dart-define=API_BASE_URL`، فاتشحنوا بعنوان محاكي أندرويد
(`10.0.2.2`). `assertProductionApiConfig()` رمى `StateError` زي ما هو مصمّم — بس **قبل أول frame**،
وFlutter بيمنع شبّاك أندرويد يترسم لحد أول frame. النتيجة على موبايل المالك: الـsplash ثابت،
وأول لمسة → «التطبيق لا يستجيب» (ANR). على التطبيقين. البناء نجح والرفع نجح ولا خطوة قالت
إن فيه حاجة غلط.

اتقفلت بتلات طبقات، كل واحدة بتمسك لو اللي قبلها اتخطّت:

| الطبقة | فين | بتمسك إيه |
|---|---|---|
| حارس بناء | `android/app/build.gradle.kts` (التطبيقين) | أي `assemble/bundle*Release` بلا عنوان https للإنتاج **مابيبنيش أصلاً** — مهما كان مين اللي بيبني |
| فحص الناتج | `scripts/build-play-release.sh` | العنوان **متخبّز فعلاً** جوّه `libapp.so` في الـAAB/APK، مش بس اتكتب في الأمر |
| شاشة فشل | `lib/core/startup_failure_app.dart` | لو أي حاجة فشلت قبل `runApp`، الشاشة **بتترسم** برسالة بدل splash متجمّد |

الحارس الوقت-تشغيل (`assertProductionApiConfig`) **لسه شغّال بنفس الصرامة** — شاشة الفشل
مابتشغّلش التطبيق، بتقفل عليه برسالة. الفرق إن فشله بقى مرئي من لقطة شاشة واحدة.

#### يدويًا (لو لازم)

```bash
flutter build appbundle --release --dart-define=API_BASE_URL=https://api.ostahome.com/api/v1
```

من غير `--dart-define` حارس Gradle بيرفض البناء برسالة بتقول السبب والأمر الصح.

### ٢) على الجهاز — الحد الأدنى اللي مايتخطّاش

| # | الخطوة | الفشل معناه |
|---|---|---|
| ١ | التطبيق بيفتح ومابيقفلش فورًا | R8 شال حاجة لازمة |
| ٢ | تسجيل دخول بـOTP حقيقي على HTTPS | الشبكة/الشهادة/بوابة SMS |
| ٣ | حجز كامل: خدمة ← ميعاد ← سعر ← تأكيد | فك JSON اتكسر بالـminification |
| ٤ | رفع صورة من الكاميرا | أذونات/تخزين |
| ٥ | **إشعار push والتطبيق مقفول تمامًا** | FCM أو القناة الافتراضية |
| ٦ | **الضغط على الإشعار بيفتح الشاشة الصح** | deep link — اتفحص آليًا بس التنفيذ الحقيقي بيثبت الملاحة |
| ٧ | الشات اللحظي (Socket.IO) | WebSocket خلف HTTPS/بروكسي |

الخطوة ٥ و٦ **مايتنفّذوش على محاكي بلا Google Play Services**.

### ٣) الشبكة الحقيقية

- جرّب على **بيانات المحمول** مش واي-فاي بس — CGNAT وMTU بيكشفوا حاجات مختلفة.
- جرّب **نت بطيء** (Android: Developer options → Network throttling) — تفاصيل ج-١٦.

## ليه deep links أخطر بند في القايمة

الباك-إند بيبعت `deep_link` مع الإشعار والتطبيق بيوجّه بيه. أي نمط بيتبعت والتطبيق مش عارف
يقراه = **العميل بيضغط الإشعار وماينفتحش حاجة**: مفيش خطأ، مفيش لوج، مفيش أي أثر. عطل صامت
بالكامل — ومستحيل يتلاحظ من غير فحص مقارن.

`scripts/release-readiness-audit.js` بيستخرج **كل** أنماط `deepLink:` من الباك-إند ويقارنها
براوتر كل تطبيق. **شغّله بعد أي إشعار جديد** — إضافة `deepLink` جديد بلا مسار في الراوتر هي
بالظبط الحالة اللي بتعدّي من كل المراجعات.
