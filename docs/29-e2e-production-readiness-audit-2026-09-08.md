# 29 — تدقيق End-to-End لجاهزية الإنتاج (2026-09-08)

> **Audit baseline**: `claude/home-repair-company-project-hgotr7` @ `35d5aea`
> **الطريقة**: تنفيذ حي على API شغّال + Postgres/Redis حقيقيين — مش قراءة كود. كل نتيجة تحتها
> إعادة إنتاج فعلية أو `file:line` دقيق.
> **النطاق**: تدقيق فقط. **مفيش سطر كود اتغيّر.** التنفيذ في جلسة تانية.

## 0. ملخص تنفيذي

اتعمل مشي شجري على المنتج كله (عميل → حجز → دفع → إلغاء → أدمن)، ومحاولات كسر متعمّدة
(خروج عن الترتيب، ضغط مزدوج، تزامن، مدخلات خبيثة، ضغط حِمل).

**النتيجة الحاكمة**: النظام **مايستحملش ٢٠ حجز متزامن**. عند ٢٠ طلب في نفس اللحظة، زمن
الاستجابة بيقفز من **٠.٤ ثانية لـ١٠.٨ ثانية**، وعند ٤٠ بيبدأ يرجّع **500** للعميل. السبب
جذري ومعروف بالظبط دلوقتي (بند **P0-1**) — مش «السيرفر صغير».

| الخطورة | العدد | البنود |
|---|---|---|
| 🔴 **P0 — مانع إطلاق** | 4 | P0-1 … P0-4 |
| 🟠 **P1 — خطر مالي/تشغيلي حقيقي** | 5 | P1-1 … P1-5 |
| 🟡 **P2 — تجربة مستخدم واحترافية** | 6 | P2-1 … P2-6 |
| ⚪ **P3 — بقايا وتنضيف** | 3 | P3-1 … P3-3 |

**اللي اشتغل صح** (مهم زي اللي غلط) — القسم ٦.

## 1. 🔴 P0 — موانع إطلاق

### P0-1 — قفلة الـConnection Pool: النظام بيتجمّد عند ١٠ حجوزات متزامنة

**ده أخطر بند في التقرير كله.**

#### القياس الحي

| عدد الطلبات المتزامنة | p50 | أقل زمن | النتيجة |
|---|---|---|---|
| ٥ | ٤٧٩ms | ٤٧٢ms | ٥×201 ✅ |
| ١٠ | ٤٣٧ms | ٤١٧ms | ١٠×201 ✅ |
| **٢٠** | **١٠٫٨٢٤ ثانية** | **١٠٫٧٩ ثانية** | ٢٠×201 (بعد تعليق) |
| **٤٠** | **١٠٫٨٥ ثانية** | — | **٣٨×201 + ٢×500** ❌ |

لاحظ إن **أقل** زمن في موجة الـ٢٠ هو ١٠.٧٩ ثانية — يعني **مفيش ولا طلب واحد عدّى بسرعة**.
ده مش ازدحام تدريجي، ده **قفلة**.

#### السبب الجذري — مثبت

عيّنات `pg_stat_activity` أثناء الحِمل بتقول نفس الحاجة ١٢ مرة ورا بعض:

```
idle in transaction | Client | ClientRead | SELECT EXISTS (SELECT 1 FROM technician_work_opportunities …
```

`idle in transaction` + `ClientRead` معناها: **Postgres فاتح ترانزاكشن ومستني التطبيق يبعت
الأمر اللي بعده** — والتطبيق مشغول بحاجة تانية وهو ماسك الاتصال.

الكود:

```ts
// apps/api/src/modules/matching/matching.service.ts:1228
const result = await this.dataSource.transaction(async (manager) => {   // ← اتصال (أ) اتحجز
  …
  const decision = await this.scheduledDispatchDecision(order, manager); // :1238
  //                     └─> firstScheduledCandidate(order)
  //                          └─> findEligibleTechnicians()
  //                               └─> this.dataSource.query(…)          // :298 ← اتصال (ب)!
  const candidate = await this.firstScheduledCandidate(order);           // :1240 ← اتصال (ب) تاني
```

`findEligibleTechnicians()` في `matching.service.ts:298` بتنفّذ استعلامها بـ
**`this.dataSource.query()`** — يعني **بتسحب اتصال جديد من الـpool** بينما الترانزاكشن
الأصلي لسه ماسك اتصال.

مع `DATABASE_POOL_MAX = 10` (`src/config/configuration.ts:14`):

1. ١٠ طلبات متزامنة بتاخد الـ١٠ اتصالات كلها وتفتح ترانزاكشن.
2. كل واحد فيهم بيطلب اتصال **حادي عشر**.
3. الـpool فاضي، ومحدش يقدر يسيب اتصاله لأنه هو نفسه مستني.
4. **قفلة كاملة** لحد `connectionTimeoutMillis = 10000` (`configuration.ts:15`).

ده بيفسّر الـ١٠.٨ ثانية بالظبط، وبيفسّر ليه **كل** الطلبات اتأخرت مش نصهم.

#### المدى — مش مكان واحد

كاشف call-graph لقى **٩ مواضع** بتعمل نفس الحاجة:

| الملف | السطر | الاستدعاء |
|---|---|---|
| `matching.service.ts` | 848, 883, 902, 908, 917, 930 | `findEligibleTechnicians()` جوّه ترانزاكشن `tx@752` |
| `matching.service.ts` | 1238 | `scheduledDispatchDecision()` |
| `matching.service.ts` | 1251 | `classifyCandidate()` |
| **`payments.service.ts`** | **3813** | **`getCollectionBreakdownForOrder()` — مسار فلوس** |

> **ليه التدقيقات السابقة مالقتهوش**: الهروب بيحصل **عبر حدود دالة** — مفيش
> `this.dataSource` مكتوب حرفيًا جوّه بلوك الترانزاكشن، فأي `grep` بيرجع صفر. لازم تحليل
> call-graph.

#### الحل (بالترتيب)

1. **الإصلاح الجذري** — تمرير الـ`manager` للآخر. كل دالة بتتنادى جوّه ترانزاكشن لازم تاخد
   `manager?: EntityManager` وتستخدم `const executor = manager ?? this.dataSource`
   (النمط ده **موجود بالفعل وصح** في `technician-work-opportunities.service.ts:93`،
   فهو مش اختراع جديد — هو توحيد لنمط قايم).
   - `findEligibleTechnicians(order, …, manager?)`
   - `firstScheduledCandidate(order, manager?)`
   - `classifyCandidate(…, manager)` (بتاخده أصلاً — تأكد إنه بيتمرر لجوّه)
   - `getCollectionBreakdownForOrder(orderId, manager?)`
2. **حارس بنيوي يمنع التكرار** — قاعدة ESLint مخصوصة أو اختبار وحدة بيمشي على AST ويفشل لو
   دالة بتستخدم `this.dataSource` اتنادت من بلوك ترانزاكشن. من غيره البَقّة هترجع.
3. **اختبار انحدار** — spec بيفتح `POOL_MAX=2` ويطلق ٤ طلبات متزامنة: لازم يعدّوا كلهم في
   أقل من ثانية. ده بيثبّت الإصلاح للأبد.
4. **بعد الإصلاح بس**، أعِد قياس الـpool. `max=10` كان قرار متعمّد موثّق في
   `database.module.ts:19-24` («تكبير الـpool بيداري استنزافًا مش بيمنعه») — والكلام ده
   **صح**، فالترتيب لازم يكون: صلّح التسريب الأول، وبعدين عاير الرقم على حِمل حقيقي.

### P0-2 — `trust proxy` مش متضبط: كل عملاء المنصة في دلو throttle واحد

**الحقيقة**: `trust proxy` **مش موجود في المستودع كله**:

```bash
$ grep -rn "trust proxy\|trustProxy" apps/api/src     # صفر نتايج
```

`main.ts` (٥٧ سطر) و`http-bootstrap.ts` مافيهمش أي `app.set('trust proxy', …)`.

**الأثر في الإنتاج** (خلف load balancer زي Railway):

- Express بيرجّع `req.ip` = **IP بتاع الـload balancer**، مش العميل.
- `@nestjs/throttler` من غير `getTracker()` مخصوص بيتعقّب بالـ`req.ip` (اتأكدت: مفيش أي
  `getTracker` في المستودع).
- **يعني كل عملاء المنصة بيتحسبوا شخص واحد.**
  - السقف العام ٦٠ طلب/دقيقة (`app.module.ts:72`) → **المنصة كلها بتقف عند ١ طلب/ثانية**.
  - `/auth/otp/request` سقفه ٥/دقيقة (`auth.controller.ts:27`) → **٥ عمليات تسجيل دخول
    للمنصة كلها في الدقيقة**.

ده اتأكد عمليًا: في التدقيق ده، جهاز واحد استهلك السقف وخلّى **كل** النداءات ترجع 429.

**كمان**: كل `audit_logs.ip_address` و`security_events` هيسجّلوا IP الـload balancer — يعني
سجل الأمان بيبقى بلا قيمة تحقيقية.

#### الحل

1. `app.set('trust proxy', 1)` في `configureHttpLayer()` — **الرقم مش `true`**. `true`
   بيخلّي أي حد يزوّر `X-Forwarded-For` وياخد هوية غيره؛ الرقم بيحدد كام proxy موثوق.
2. تثبيته بـenv (`TRUSTED_PROXY_HOPS`) لأن العدد بيختلف بين Railway وnginx محلي.
3. `getTracker()` مخصوص: للمستخدم المسجّل استخدم `user.sub`، وللزائر استخدم الـIP. كده
   عميل مسجّل ماينفعش ييجي عليه throttle بسبب عميل تاني على نفس الـNAT.
4. **حتى بعد الإصلاح**: `/auth/otp/request` بـ٥/دقيقة **لكل IP** لسه خطر في مصر — شركات
   المحمول بتستخدم CGNAT وآلاف المشتركين بيتشاركوا IPs معدودة. القاعدة تبقى **بالرقم
   المطلوب** (`phone_number`) مش بالـIP، وده كمان أدق أمنيًا (بيمنع قصف رقم بعينه).
5. اختبار: نداء بـ`X-Forwarded-For` مزوّر لازم **ما**يغيّرش هوية الـthrottle.

### P0-3 — تاريخ في الماضي بيولّد طلب «طوارئ» بسعر أعلى ٢٠٪

#### إعادة الإنتاج الحية

على خدمة `allows_emergency = true`:

| `scheduled_at` المُرسل | النتيجة |
|---|---|
| أمس | `201` — `booking_mode: **emergency**`, `searching_technician` |
| `2024-03-15` (من سنتين) | `201` — `booking_mode: **emergency**`, `searching_technician` |
| `1970-01-02` | `201` — `booking_mode: **emergency**`, `searching_technician` |
| `9999-12-31` | `201` — `booking_mode: individual`, `searching_technician` |

#### السبب الجذري

```ts
// apps/api/src/modules/orders/booking-mode-resolver.ts:55
export function isSameDayUrgent(input: UrgencyInput): boolean {
  if (!input.scheduledAt) return false;
  const today = platformDayOf(input.now ?? new Date());
  return platformDayOf(input.scheduledAt) <= today;   // ← "أقل من أو يساوي"
}
```

`<= today` معناها **أي تاريخ في الماضي بيتعامل كأنه النهارده**. ومفيش أي رفض صريح لتاريخ
ماضي في مسار الإنشاء، ومفيش **أي حد أقصى** للتاريخ المستقبلي (اتأكدت: مفيش أي إعداد
`booking horizon` في المستودع).

#### الأثر المالي — مش نظري

```
pricing.emergency_surcharge_percentage   = 20
commission.emergency_adjustment_percentage = 5
```

يعني **ساعة غلط في موبايل العميل، أو باج توقيت في الواجهة، أو فورم قديمة متخزّنة =
العميل بيتحاسب +٢٠٪ من غير ما يطلب طوارئ**. وده بالظبط نوع «الفلوس بتتاخد غلط» اللي
مايتقبلش.

**وأثر تشغيلي**: طلب بتاريخ 1970 بيتوزّع على فني كطوارئ، وبيفضل «متأخر» بشكل دائم على رأس
قايمة الفني (ADR-0035 قسم «متأخر»)، وبيلخبط كاشف الـworkflow العالق. وطلب سنة 9999
بيفضل في `searching_technician` **للأبد** وبيلوّث تخطيط الطاقة والإحصائيات.

#### الحل

1. رفض صريح ومبكر في `CreateOrderDto` + `order-creation.service.ts`:
   - `scheduled_at` قبل بداية اليوم الحالي بتوقيت `Africa/Cairo` → `400` برسالة
     **«التاريخ ده عدّى — اختار يوم من النهارده أو بعده»**.
   - **مش** يتعامل كأنه النهارده. الصمت هنا هو البَقّة.
2. حد أقصى للحجز المسبق من `settings` (مقترح `orders.max_advance_booking_days = 90`)،
   ورسالة واضحة لو اتعدّى.
3. تصحيح `isSameDayUrgent` لـ`=== today` بالظبط، وتخلية الماضي مسؤولية طبقة التحقق —
   عشان الدالة تبقى صادقة مع اسمها.
4. **الأهم**: نفس الفحص لازم يتحط في `preview` و`create` بنفس الحرف. الفرق بينهم هو مصدر
   شكوى «الأدمن بيحفظ والعميل بياخد error» المتكررة.
5. Migration تصحيحية: الطلبات القايمة اللي `scheduled_at` بتاعها خارج نطاق معقول تتعلّم
   للمراجعة (مش تتمسح تلقائي — فيها فلوس محتمَلة).

### P0-4 — مفيش idempotency على إنشاء الطلب: دوسة مزدوجة = طلبين

#### إعادة الإنتاج

طلبين متوازيين بنفس الـbody بالظبط:

```
201  parallel create #1   OK
201  parallel create #2   OK
distinct orders created: 2
```

**التناقض الداخلي هو الدليل**: `POST /orders/:id/pay-with-wallet` بيرفض من غير
`Idempotency-Key` («Idempotency-Key header مطلوب») — يعني المفهوم **متبني ومطبَّق في
المشروع بالفعل**، بس مش مطبَّق على **الـendpoint اللي العميل بيدوس عليه أكتر حاجة**.

#### ليه ده خطير مع P0-1

البندين بيتضاعفوا: مع القفلة (P0-1) الطلب بياخد **١١ ثانية**. العميل هيفتكر إن التطبيق
علّق و**هيدوس تاني** — فيتعمل طلب مكرر، ويتوزّع على فني، ويترتب عليه رسوم إلغاء لما يلغيه.

#### الحل

1. `Idempotency-Key` إجباري على `POST /orders` بنفس آلية الدفع الموجودة (توحيد، مش بناء
   جديد — دوّر على الـinterceptor/decorator المستخدم في `pay-with-wallet` ووسّعه).
2. جدول/مفتاح idempotency بـTTL معقول (٢٤ ساعة) بيخزّن الرد الأصلي ويرجّعه حرفيًا عند
   التكرار — **مش** `409`. العميل المتردد لازم يشوف طلبه، مش خطأ.
3. حماية تانية على مستوى الـDB: unique partial index على
   `(customer_id, service_id, address_id, scheduled_at)` للحالات النشطة، كشبكة أمان لو
   الـheader ضاع.
4. في التطبيقات: تعطيل الزرار فورًا بعد أول دوسة + مؤشر تحميل. لكن ده **تحسين UX مش
   حماية** — الحماية لازم تكون في السيرفر.

## 2. 🟠 P1 — مخاطر مالية وتشغيلية

### P1-1 — «الفلوس غير المسوّاة = 0» بيقيس الحاجة الغلط

السطر اللي المالك سمّاه **«آخر سطر وأهم سطر»** بيفحص **٣ ثوابت داخلية لدفتر المحفظة بس**
(`financial-dashboard.service.ts:301-443`):

1. رصيد المحفظة = مجموع حركاتها
2. حساب الصف: `balance_after = balance_before ± amount`
3. سلسلة متصلة بين الحركات

**اللي مش بيتفحص خالص** — وده اللي «فلوس ضايعة» بمعناها الحقيقي. من قاعدة البيانات الحية
دلوقتي:

| الحالة | العدد الفعلي |
|---|---|
| `refunds` عالقة في `processing` | **٦** |
| طلبات `completed` لكن `payment_status = unpaid` | **١٥** |
| طلبات عالقة في `searching_technician` أكتر من يوم | **٦٧** |

الستّة دول فلوس **اتحجزت للعميل ومارجعتش وماتقفلتش**. اللوحة مش شايفاهم أصلاً.

**وأسوأ**: `grep` بيثبت إن `RefundStatus.PROCESSING` موجودة في **ملف واحد مش-spec بس**
(`payments.service.ts`) — يعني:
- **مفيش أي sweep** بيراجع الاستردادات العالقة.
- **مفيش أي شاشة** بتعرضها.

ومسار «نتيجة غير معروفة من البوابة» (`payments.service.ts` — فرع
`providerOutcome === 'unknown'`) بيكتب سطر audit `order.refund_reconciliation_required`
وبيسيب الاسترداد `PROCESSING` **للأبد** — سطر في جدول تدقيق محدش بيقراه.

#### الحل

1. توسيع `reconciliationCheck()` لأربع عائلات إضافية، كل واحدة سطر مستقل بعدد ومبلغ:
   - استرداد `processing` عدّى عليه أكتر من X ساعة
   - دفعة `pending`/`processing` عدّى عليها أكتر من X ساعة
   - طلب ملغي بـ`payment_status='paid'` وملوش استرداد مكتمل
   - طلب `completed` بـ`payment_status='unpaid'`
2. **فصل «مخالفة» عن «ضجيج قديم»**: القاعدة الحالية فيها ٦١٧ مخالفة دفترية (١٢ رصيد +
   ٦٠٥ سلسلة) أغلبها من بيانات اختبار متراكمة من شهور. **فحص مستحيل يوصل صفر = فحص محدش
   بيبصله.** لازم `baseline_before` (تاريخ/رقم حركة) بحيث يتقاس اللي بعد الإطلاق بس.
3. Sweep دوري (`runExclusiveSweep` موجود بالفعل — ADR-0076) بيصعّد الاستردادات العالقة
   لقايمة عمل بشرية.
4. شاشة أدمن للاستردادات المعلّقة بأزرار فعل — الاسترداد يدوي بقرار إنسان (سياسة المالك)،
   بس **لازم يبقى ظاهر** عشان الإنسان يقدر يقرر.

### P1-2 — الحجز/الإفراج في المحفظة بيحرّك فلوس **من غير قيد دفتري**

```ts
// apps/api/src/modules/payments/wallets.service.ts:291-302
async reserveForPayout(walletId, amountCents, manager) {
  …
  wallet.balanceCents -= amountCents;          // ← فلوس خرجت
  wallet.reservedBalanceCents += amountCents;  // ← فلوس دخلت
  return manager.save(wallet);                 // ← وخلاص. مفيش wallet_transaction
}
```

نفس الحاجة في `releaseReservation()` (:316-324).

وبعدين `finalizePayout()` (:356) بتكتب قيد debit، والتعليق نفسه بيعترف:

```ts
const walletBalanceBefore = wallet.balanceCents; // مبيتغيّرش (كان اتخصم وقت الحجز)، بنسجله كمرجع بس
```

يعني القيد بيسجّل `balance_before/after` **مش بيعبّروا عن تغيير حقيقي حصل في
`balance_cents`** — لأن الفلوس خرجت وقت الحجز بلا قيد.

**الأثر**: أول ما أول عملية صرف حقيقية تحصل في الإنتاج، **الثابتة رقم ١ والثابتة رقم ٣ في
لوحة التسوية هيتكسروا رياضيًا** — واللوحة هتفضل حمرا للأبد لسبب مش حقيقي.

> **ملاحظة أمانة**: القاعدة الحالية فيها **صفر payouts**، فالمخالفات الـ١٢ الموجودة دلوقتي
> **مش** من المسار ده. ده عيب **كامن** هيظهر أول يوم صرف حقيقي، مش عيب ظاهر دلوقتي.

#### الحل

1. الحجز والإفراج يتكتبوا كقيود حقيقية بنوعين جداد
   (`payout_reserve` / `payout_release`)، أو
2. تعديل الثابتة رقم ١ لتبقى
   `balance_cents + reserved_balance_cents = Σ(الحركات)` — وده أبسط وأصدق مع النموذج
   الحالي، ويتوثّق في ADR.
3. أيًا كان الاختيار — **اختبار حي**: احجز، أفرج، اصرف، وبعد كل خطوة شغّل
   `reconciliationCheck()` ولازم ترجع صفر.

### P1-3 — ٦٧ طلب عالق في `searching_technician` بلا مخرج

من القاعدة الحية: **٦٧ طلب** قاعدين في `searching_technician` أكتر من ٢٤ ساعة.

من الـstate machine (`order-state-machine.ts:73-80`) كمان: **`IN_PROGRESS` ملهاش أي مسار
إلغاء خالص** — لا من العميل، لا من الفني، ولا من النظام. الوحيد المتاح `WORK_COMPLETED`
أو `DISPUTED`. يعني طلب دخل التنفيذ ووقف (الفني اختفى مثلاً) **مايتقفلش أبدًا** إلا
بتحويله لنزاع.

#### الحل

1. تحديد «عمر أقصى» لكل حالة غير نهائية في مكان واحد (جدول/إعداد)، وsweep بيصعّد اللي
   بيتعداه لمركز العمليات (الـExceptions Center موجود بالفعل — Ops-3).
2. إضافة `CANCELLED_BY_SYSTEM` كانتقال مسموح من `IN_PROGRESS` **بقرار أدمن موثّق بس**
   (مش تلقائي — فيه فلوس وشغل فعلي).
3. تنضيف الـ٦٧ الحاليين بمراجعة يدوية، مش batch أعمى.

### P1-5 — رسوم الإلغاء بتتحسب من قيمة قديمة قبل القفل


`order` هنا اتقرى في السطر ٥١ **قبل** الترانزاكشن والقفل (:105-118). لو السعر اتغيّر بين

   الحجز؟ — أي واحد فيهم مقبول، بس **لازم يتكتب ويتنفّذ**، مش يفضل معلّق.
3. الرسوم غير المحصّلة تتفصل في تقارير الإيراد عن المحصّلة فعلاً.

## 3. 🟡 P2 — تجربة المستخدم والاحترافية

### P2-1 — رسايل الأخطاء نُصّها إنجليزي تقني

المنتج كله عربي، والأخطاء دي رجعت من نداءات حقيقية:

| الحالة | الرسالة اللي العميل بيشوفها |
|---|---|
| ضغط زايد | **`ThrottlerException: Too Many Requests`** |
| لينك/معرّف غلط | **`Validation failed (uuid is expected)`** |
| اسم طويل | **`full_name must be shorter than or equal to 120 characters`** |
| عنوان ناقص | **`area_id must be a UUID`** |
| تاريخ غلط | **`scheduled_at must be a valid ISO 8601 date string`** |
| طريقة دفع | **`payment_method must be one of the following values: card, instapay, fawry_reference`** |
| كمية سالبة | **`pricing_quantity must be a positive number`** |

`ThrottlerException` تحديدًا **بتفضح اسم كلاس داخلي** للمستخدم.

في المقابل، الرسايل المكتوبة بإيد الفريق ممتازة فعلاً:
«الخدمة دي مش متاحة لنفس اليوم — اختار يوم تاني»، «مينفعش تستخدم كود خصم وكود عمارة مع
بعض»، «حالة الطلب اتغيّرت بالفعل — حاول تاني». **فالمشكلة مش في القدرة، المشكلة إن
class-validator الافتراضي بيعدّي من غير ترجمة.**

#### الحل

1. `exceptionFactory` مخصوص في الـ`ValidationPipe` العام بيترجم أنواع الأخطاء القياسية
   (`isUuid`, `maxLength`, `isEnum`, `isDateString`, `isPositive`, `whitelistValidation`)
   لرسايل عربية مبنية من اسم الحقل + قاموس أسماء عربية.
2. فلتر خاص لـ`ThrottlerException` يرجّع
   **«حاولت كتير في وقت قصير — استنى دقيقة وجرّب تاني»** مع `Retry-After`.
3. `ParseUUIDPipe` مخصوص برسالة **«اللينك ده مش صحيح أو قديم»**.
4. **اختبار يمنع الرجوع**: spec بيمشي على عيّنة من كل الـDTOs، يبعت مدخلات غلط، ويفشل لو
   أي رسالة رجعت من غير حرف عربي. من غيره أول DTO جديدة هترجّع المشكلة.

### P2-2 — ترتيب الأخطاء بيخفي السبب الحقيقي — ✅ تم الإصلاح في 2026-09-08

تقييم طلب ملغي رجّع:
`property rating should not exist | overall_rating must not be greater than 5…`
بدل «الطلب ده ملغي». والـValidationPipe بيشتغل **قبل** فحص الملكية والحالة، فالعميل بياخد
رسالة عن حقل بدل رسالة عن الموقف.

**التنفيذ**: الحقول اللي بتحدد الهوية/الحالة (`:id`) تتفحص في guard قبل الـbody لمسار تقييم
العميل. الطلب الملغي يرجع سبب الإلغاء حتى لو جسم التقييم قديم أو غير صحيح، والخدمة تعيد الفحص
وقت الحفظ لمنع أي سباق بين الحارس والتنفيذ.

### P2-3 — عقد `payment_method` مايعرفش يعبّر عن «كاش» — ✅ تم الإصلاح في 2026-09-08

`POST /orders` بيرفض `payment_method: 'cash'` رغم إن الخدمة `cash_allowed = true` وفيه
مسار كاش كامل. الحقل عمدًا للدفع **المسبق** بس (`create-order.dto.ts` التعليق واضح: كاش
يعني تسيب الحقل فاضي).

القرار سليم، **الاسم غلط**. أي مطوّر/سيشن جديدة هتبعت `'cash'` وتاخد 400، والرسالة
مابتقولش «سيب الحقل فاضي للكاش».

**التنفيذ**: عقد الإنشاء صار `prepayment_method`، مع دعم `payment_method` القديم مؤقتًا. الكاش
والوسائل اللاحقة يرجعون رسالة عربية صريحة بدل خطأ enum تقني، وأي تعارض بين الاسمين يرفض الطلب.
تقول «للدفع كاش سيب الحقل ده فاضي»، وتوثيق البند في `docs/02`.

### P2-4 — «إعادة الجدولة» بلا سبب مسجّل — ✅ تم الإصلاح في 2026-09-08

`RescheduleOrderDto` فيه `new_slot_id` / `new_scheduled_at` / `new_scheduled_end_at`
**وبس** — مفيش `reason`. بينما الإلغاء السبب فيه **إجباري** لما الأدمن يعرّف أسباب.

يعني عميل يقدر يأجّل الطلب مرة ورا التانية والفني بيخسر يومه، ومفيش أي بيانات تقول ليه.

**التنفيذ**: العميل يرسل سببًا اختياريًا من قائمة مع توضيح حر عند «سبب آخر»، ويُكتب في
Timeline. عدّاد `customer_reschedule_count` يزيد داخل قفل الطلب نفسه، وله حد قابل للضبط
(`orders.customer_reschedule_max_count`، افتراضي 3). بعد الحد يتحول المسار للدعم بدل إنشاء
رسوم أو خصم تلقائي غير معتمد.

### P2-5 — حروف تحكّم اتجاه النص بتتخزّن خام

`problem_description: '🔧‮مشكلة‬'` اتقبل بـ201. الحرف `U+202E` (RIGHT-TO-LEFT OVERRIDE)
بيقلب اتجاه النص اللي بعده بصريًا في أي شاشة (أدمن، تطبيق الفني) — ناقل معروف لتزوير
العرض.

**الحل**: تنضيف حروف التحكم الثنائية الاتجاه (`U+202A`–`U+202E`, `U+2066`–`U+2069`) في
transformer عام على كل حقول النص الحر عند الإدخال.

### P2-6 — الفشل تحت الضغط بيظهر كـ500 مبهم

عند ٤٠ طلب متزامن، عميلين شافوا:
**`500 — حصل خطأ غير متوقع، حاول تاني`**

السبب الحقيقي كان انتهاء مهلة الحصول على اتصال DB (P0-1). الرسالة مابتفرّقش بين «النظام
مزحوم دلوقتي» و«حصل خطأ في طلبك».

**الحل**: مهلة الـpool تترجم لـ`503` + **«النظام مزحوم شوية دلوقتي — جرّب كمان شوية»**
مع `Retry-After`. الفرق مهم: العميل يعرف إن طلبه سليم وإن الإعادة هتنفع.

## 7. اللي **ما**اتفحصش (بأمانة)

عشان التقرير مايتقريش أوسع مما هو:

- **أفعال الكتابة عند الأدمن** — وقفت عند بوابة MFA. اللي اتفحص هو القراءة والبنية بس.
  محتاج جلسة أدمن كاملة بـMFA لتغطية الإلغاء/الاسترداد/التعيين القسري حيًا.
- **مسارات الدفع الخارجية الحقيقية** (Paymob، Fawry) — البوابات مش موصّلة في البيئة دي.
  اتفحص المنطق والعقود بس، مش نداء حقيقي.
- **تطبيقات Flutter** — مااتشغّلوش بصريًا في التدقيق ده.
- **الويب سوكت تحت ضغط** (تتبّع لحظي، شات) — مااتحمّلش.
- **مسار الضمان وإعادة الزيارة** — مااتمشيش end-to-end.
- **الـ٦٠٥ مخالفة سلسلة في الدفتر** — اتأكد إنها **مش** من مسار الصرف (مفيش payouts في
  القاعدة)، وأغلب المؤشرات إنها بيانات اختبار متراكمة من جلسات سابقة بتكتب SQL خام. **لكن
  مااتثبتش نهائيًا**، وده لازم يتقفل مع P1-1.
