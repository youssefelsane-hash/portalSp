# ADR-0114 — تتبّع أخطاء الواجهة ومراقبة الموقع العام

- **الحالة**: مقبول
- **التاريخ**: 2026-09-25
- **يمسّ**: `ops` (جدول + مسار استقبال + إشارة إنذار)، `customer-web`، `admin`
- **بيعيد استخدام**: `OpsMetricsService` (لوحة الإشارات الواحدة)، `RequestMetricsService`،
  عتبات `ops.alert_*` من محرك الإعدادات، `@Public()` + `@Throttle` بنفس نمط `seo`

## ١. الطلب

> «نظام يسجّل: الصفحة اللي حصل فيها الـError، نوع الـError، المتصفح/الجهاز، الوقت، وأي API فشل…
> تعرف إن ٣٧ مستخدم حصل لهم Error عند اختيار الموعد النهاردة من غير ما تستنى حد يكلّم الدعم.»
>
> «المونيتورينج: API uptime، website uptime، الداتابيز، معدل الأخطاء، زمن الاستجابة — والمراقبة
> والتنبيهات موجودة أصلاً، عايز الموقع العام يدخل نفس النظام.»

## ٢. القرار الحاكم: **إشارة جديدة في نظام قايم، مش نظام مراقبة تاني**

المراقبة موجودة فعلاً ومبنية صح: `GET /admin/ops/health-metrics` بيرجّع `status` +‏ `alerts[]`،
وقاعدة الإنذار الخارجية كلها سطر واحد: `status != "ok"` (ج-٧، `ops/README.md`).

فأخطاء الواجهة **مش لوحة منفصلة**: بتتحوّل لإشارة جوّه نفس الرد بعتبة من الإعدادات
(`ops.alert_client_errors_per_hour`). لو عملناها نظام تاني بلوحة تانية وإنذار تاني، بيبقى عندنا
مكانين نبصّ فيهم — وده نفس الخطأ اللي §ج-٧ اتعمل عشان يقفله («مبعثرين = مفيش إنذار»).

## ٣. الجدول: `client_error_events`

لا يوجد أي مخزن لأخطاء الواجهة في النظام دلوقتي (`grep client_error|telemetry` = صفر). الموجود
حاليًا كله **من ناحية السيرفر**: `RequestMetricsService` (نسبة 5xx في نافذة زمنية، في الذاكرة)
و`.dev-logs/errors.log` (**متوقّف في الإنتاج عمدًا**). يعني خطأ بيحصل في متصفح العميل — رندر
مكسور، شبكة قاطعة، استدعاء بيرجع 400 — مفيش أي أثر له خالص. ده الفجوة الحقيقية.

| عمود | نوع | ليه |
|---|---|---|
| `app` | `text` | `customer-web` / `admin` — نفس المسار بيخدم الاتنين، والتجميع لازم يفصلهم |
| `kind` | `text` | `render` / `api` / `network` / `unhandled_rejection` / `not_found` |
| `page_path` | `text` | **المسار المطهّر**: القيم المتغيرة بتتحوّل لـ`:id` قبل الإرسال |
| `error_name` | `text` | `TypeError`، `ApiError`… |
| `error_message` | `text(500)` | مقصوص — رسالة طويلة مش بتزود معلومة |
| `component_stack` | `text(4000)` | من `error.tsx`؛ مقصوص |
| `api_path` | `text` | المسار اللي فشل، بعد تطهير الـUUIDs |
| `api_status` | `int` | كود الرد لو فيه |
| `browser` / `os` / `device_kind` | `text` | **مشتقّة في السيرفر** من `user-agent` |
| `fingerprint` | `text` | `sha256(app|kind|page_path|error_name|api_path|api_status)` — مفتاح التجميع |
| `visitor_hash` | `text` | `sha256(ip + user-agent + pepper يومي)` — لعدّ «٣٧ مستخدم» |
| `user_id` | `uuid null` | لو الطلب جاله توكن صالح بس |
| `occurred_at` | `timestamptz` | وقت السيرفر، مش وقت العميل |

**ليه `visitor_hash` مش الـIP**: عدّ «كام مستخدم» محتاج تمييز، مش هوية. الهاش بملح بيتغيّر كل
يوم بيدّي العدد الصح لليوم و**بيمنع التتبّع عبر الأيام** — وده الفرق بين قياس وبين بناء ملف عن
زائر. الملح مشتقّ من سر السيرفر + تاريخ اليوم، فمش مخزّن ولا بيتسرّب.

**ليه المتصفح/الجهاز بيتحسبوا في السيرفر**: العميل مايتصدّقش. لو بعت `browser: "Chrome"`
نستلمه زي ما هو، بقى حقل بيكتبه اللي بيهاجم. الـ`user-agent` هيدر بيوصل مع الطلب أصلاً، فالسيرفر
بيشتقّه لوحده ومايقراش أي حقل جهاز من الجسم.

### الاحتفاظ

`ops.client_errors_retention_days` (افتراضي ٣٠). التنظيف في نفس الدورة بتاعة `QueueWatchdogService`
— مش cron جديد: أخطاء الواجهة بتتقاس بالأيام، وجدول بيكبر بلا حد بقى مشكلة مراقبة بنفسه.

## ٤. المسار العام — نقطة الكتابة الوحيدة المكشوفة، فمحسوبة بالورقة والقلم

```
POST /telemetry/client-errors   @Public()  @Throttle(30/دقيقة)
```

**لازم يكون `@Public()`**: أهم الأخطاء بتحصل قبل الدخول — شاشة اللوجن نفسها، صفحة خدمة جاية من
جوجل، مستخدم توكنه خلص. مسار محمي بتوكن كان هيسجّل كل حاجة **إلا** اللي إحنا بنبنيه عشانه.

الضوابط اللي بتخلّي ده مقبول:

1. **`@Throttle({ limit: 30, ttl: 60_000 })`** لكل IP — صفحة مكسورة بتبعت خطأ أو اتنين، مش ٣٠.
2. **DTO مقفول بـ`forbidNonWhitelisted`** (الـglobal pipe أصلاً كده) + `@MaxLength` على كل حقل
   نصي، فمفيش حقل حر ولا جسم كبير.
3. **بلا تجميع مفتوح للنصوص**: `kind` قايمة مقفولة (`@IsIn`)، ومسارات الصفحة/الـAPI بتتطهّر من
   الأرقام والـUUIDs في السيرفر تاني (مش بس في العميل) — عشان مسار فيه توكن أو رقم تليفون بالغلط
   ما يتخزّنش.
4. **الرد `202` فاضي دايمًا** — مايقولش لأي حد إذا اتخزّن ولا اتجاهل ولا اندمج مع صف موجود.
   مسار كتابة عام بيرجّع تفاصيل بيبقى أداة استكشاف.
5. **مفيش قراءة عامة خالص**: العرض تحت `admin/ops` بـ`operations.view` زي `health-metrics`
   بالظبط، لنفس السبب المكتوب هناك (أرقام تشغيلية مش للإنترنت).
6. **بيتسجّل في `scripts/security-audit.js`** في قايمة الـ`@Public()` المراجَعة مع سببه —
   الحارس ده مسك ADR-0113 فعلاً، ومش المفروض يتخطّى.

## ٥. uptime الموقع العام

`GET /api/health` في `customer-web` نفسه (Route Handler، مش صفحة): بيتأكد إن الطبقة دي قادرة
**توصل للـAPI**، وبيرجّع `ok` / `degraded`. ده اللي بيخلّي «الموقع شغّال» سؤال له جواب: صفحة
Next بترندر من الكاش وهي أصلاً مش شايفة الباك-إند بتبان شغّالة وهي مش شغّالة.

المراقبة الخارجية بتفضل بتقرا من مكانين بس: `/api/health` (طبقة الويب) و
`/admin/ops/health-metrics` (كل حاجة تانية، ودلوقتي أخطاء الواجهة جوّاها).

## ٦. المرفوض صراحةً

- **Sentry أو أي مزوّد خارجي** — نصوص الأخطاء فيها مسارات ومعرفات طلبات؛ إرسالها لطرف تالت قرار
  بيانات مش قرار مراقبة، والمالك مااتخدش فيه. البنية دي بتخلّي التحويل لمزوّد بعدين خطوة واحدة
  لو اتقرر.
- **إرسال الـstack كامل من الإنتاج** — `component_stack` مقصوص على ٤٠٠٠ حرف، والـ`stack` الخام
  مش بيتخزّن: بيكشف بنية الملفات وبيكبّر الجدول بلا فايدة تشخيصية بعد الـminify.
- **`user_id` من الجسم** — بيتقرا من التوكن لو موجود وبس. عميل يبعت `user_id` بتاع حد تاني كان
  هيلوّث كل التجميع.
