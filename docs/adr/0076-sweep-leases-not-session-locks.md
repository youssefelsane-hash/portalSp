# ADR-0076 — حصرية الدورات المجدولة: إيجار بمهلة، مش قفل مربوط بجلسة

- **الحالة**: مقبول ومُنفَّذ
- **التاريخ**: 2026-09-05
- **بيستبدل آلية**: القفل الاستشاري في `runExclusiveSweep` (تدقيق **A-2**)
- **الملفات**: `apps/api/src/common/db/sweep-lock.ts` · `infra/migrations/0272_sweep_leases.sql`

## السياق

تدقيق A-2 لقى إن كل دورة مجدولة (`setInterval`) بتشتغل على **كل** نسخة من التطبيق، فأضاف
`pg_try_advisory_lock` عشان نسخة واحدة بس تشتغل. الحصرية دي صح ولازمة (بدونها: تحصيل مكرر،
إشعار مكرر، إلغاء طلب مرتين).

**المشكلة كانت في آلية القفل، مش في فكرته.** القفل الاستشاري على مستوى الجلسة مربوط بالاتصال
اللي أخده: عشان يفضل ماسك طول الدورة، الاتصال لازم يفضل محجوز طول الدورة.

### العطل اللي حصل فعلاً (اتعاد إنتاجه، مش استنتاج)

وقت الإقلاع بيتسجّل **١٤ مؤقّت بـ٦٠ ثانية** + واحد بـ١٥ ثانية + أول تشغيل لدورة التدرّج،
وكلهم بيولعوا في نفس التِك عند الدقيقة الأولى:

| | |
|---|---|
| حجم الـpool الافتراضي في node-postgres | **١٠** |
| محجوز دايمًا لـ`LISTEN` (الإعدادات + إبطال الجلسات) | **٢** |
| متاح فعلاً | **٨** |
| دورات بتحاول تشتغل في نفس اللحظة | **١٦** |

٨ دورات بتاخد الـ٨ اتصالات كلها للأقفال، وكل واحدة فيهم بتعمل استعلامها الحقيقي جوّه الدورة
(`this.orders.query(...)` مثلاً) فتطلب اتصال تاسع. الاتصال ده مش هييجي أبدًا، لأن اللي ماسكينه
هم نفسهم اللي مستنيينه. **قفل ميت بنفسه على نفسه.**

ومفيش `connectionTimeoutMillis` مضبوطة، والافتراضي في node-postgres هو **انتظار بلا نهاية** —
فالنتيجة مكانتش بطء، كانت توقّف كامل: `/health` وطلب الـOTP وكل حركة التطبيقات بتتعلّق للأبد،
والعملية مابترجعش لوحدها حتى بعد إنهاء الجلسات من ناحية Postgres.

الشكل في `pg_stat_activity` وقت العطل: ١٠ اتصالات — ٢ `LISTEN` و٨ خاملين آخر استعلام لكل واحد
`SELECT pg_try_advisory_lock(...)`، و٨ أقفال ممنوحة في `pg_locks`.

## القرار

**إيجار بمهلة في جدول `sweep_leases`، بدل قفل مربوط بالجلسة.**

الاقتناء والتجديد والتحرير **استعلام قصير واحد** كل مرة، والاتصال بيرجع للـpool فورًا:

| العملية | الاستعلام | إمتى |
|---|---|---|
| اقتناء | `INSERT … ON CONFLICT (lock_name) DO UPDATE … WHERE expires_at <= now()` | مرة، قبل الدورة |
| تجديد | `UPDATE … WHERE lock_name = $1 AND holder_token = $2 AND expires_at > now()` | كل `ttl/3` أثناء الدورة |
| تحرير | `UPDATE … SET expires_at = now() - 1ms WHERE lock_name = $1 AND holder_token = $2` | مرة، بعد الدورة |

**ليه ده مايقدرش يستنزف الـpool:** مفيش أي اتصال محجوز طول الدورة. عدد الاتصالات اللي الدورة
بتاخدها في أي لحظة = صفر بين الاستعلامات. يعني الحد الأقصى للاتصالات اللي الدورات بتحتاجها في
لحظة واحدة هو عدد الاستعلامات القصيرة المتزامنة، مش عدد الدورات الشغّالة ولا مدتها — والفرق ده
هو كل الفرق بين تصميم بيزدحم وتصميم بيتقفل.

### التفاصيل اللي بتخلّي الضمانات مساوية للقديم

- **الحصرية**: `ON CONFLICT … DO UPDATE … WHERE expires_at <= now()` عبارة ذرّية واحدة. نسخة
  واحدة بس هي اللي بتاخد الصف؛ الباقي بيرجعوا فورًا (نفس السلوك القديم بالظبط: مش بيستنوا).
- **موت النسخة**: كان Postgres بيسيب القفل مع نهاية الجلسة. دلوقتي المهلة (`ttl`، افتراضي ٦٠
  ثانية) بتعمل نفس الشيء — الدورة بترجع تشتغل لوحدها من غير تنظيف يدوي.
- **الدورات الطويلة**: نبضة تجديد كل `ttl/3`، فلازم تفشل نبضتين ورا بعض قبل ما الإيجار يضيع.
- **التوكن (fencing)**: التجديد والتحرير مشروطين بـ`holder_token`. نسخة اتأخرت أطول من المهلة
  وضاع منها الإيجار **مش هتقدر** تحرّر إيجار بقى ملك نسخة تانية — وده اللي كان هيفتح الدورة
  لنسخة تالتة في نفس اللحظة.
- **`AbortSignal`**: لو التجديد لقى الإيجار ضاع، بتتبعت إشارة إلغاء للدورة (اختيارية — الدوال
  الحالية بتتجاهلها، والتوقيع متوافق معاها كلها من غير أي تعديل في الـ٢٠ منادي).

## البدائل اللي اتقيّمت

| البديل | ليه اترفض |
|---|---|
| **تكبير الـpool** | بيداري الاستنزاف مش بيمنعه: العيب إن كل دورة بتاكل اتصال طول عمرها، فأي سقف بيتاكل مع زيادة عدد الدورات. وده أصلاً استبعده الطلب صراحةً. |
| **`pg_advisory_xact_lock`** (قفل على مستوى الترانزاكشن) | أسوأ: بيحجز الاتصال **وكمان** بيسيب ترانزاكشن مفتوحة طول الدورة (`idle in transaction`) — اللي بيعطّل الـvacuum ويقفل صفوف بلا داعي. |
| **تمرير نفس الـ`QueryRunner` للدورة** | بيتطلب تمرير `EntityManager` جوّه كل دورة وكل خدمة بتناديها (عشرات الملفات، وترانزاكشنات متداخلة)، وبرضه بيحجز اتصال طول الدورة — بيقلّل الاستهلاك للنص، مايشيلش السبب. |
| **pool منفصل مخصّص للأقفال** | بيشيل التعارض مع pool الطلبات، بس بيفضل اتصال لكل دورة شغّالة: ١٦ اتصال إضافي × عدد النسخ. اتصالات Postgres مش رخيصة، والتصميم يفضل «اتصال محجوز لكل دورة». |
| **قفل موزّع على Redis** | Redis في المشروع معرَّف صراحةً كـ«مش مصدر حقيقة أبدًا» ومسموح يقع من غير ما يكسر أي عملية (`redis-cache.service.ts`). لو الحصرية اتعلّقت بيه، وقوعه يبقى إما إيقاف كل الدورات أو تشغيلها على كل النسخ (تحصيل مكرر). القاعدة أصلاً شرط لازم لأي دورة — فهي المكان الصح للحصرية. |

## الأثر

- **جدول جديد**: `sweep_leases` (migration 0272). صف لكل دورة — ١٨ صف. مفيش أي مساس ببيانات
  الدومين.
- **صفر تغييرات في الـ٢٠ منادي**: التوقيع متوافق للخلف (`sweep` بقت بتاخد `AbortSignal`
  اختياري، والدوال الحالية `() => this.sweep()` بتتجاهله).
- **ضمانات وقت تشغيل مضافة مع القرار ده** (مش جزء منه، بس نفس الحادثة كشفتها):
  `connectionTimeoutMillis` صريحة (كانت انتظارًا بلا نهاية)، ومراقب ضغط الـpool
  (`DbPoolMonitorService`)، وأرقام الـpool جوّه رد `/health`.
- **حارس ضد الرجوع**: `sweep-pool-starvation.spec.ts` بيفشل لو `sweep-lock.ts` رجع يستخدم
  `createQueryRunner` أو قفل استشاري.

## أثر تشغيلي مفيد

الصف بيفضل موجود بعد التحرير عمدًا (`expires_at` في الماضي + `last_released_at` + `run_count`)،
فسؤال «آخر مرة الدورة دي اشتغلت إمتى ومن أنهي نسخة» بقى استعلام واحد — وده اللي `dev-doctor.sh`
بيطبعه في قسم التشخيص.

```sql
SELECT lock_name, holder_instance, renewed_at, run_count FROM sweep_leases ORDER BY renewed_at DESC;
```
