## 0. ملاحظة صريحة قبل ما نبدأ

طلبت "أمان واستقرار 100%". لازم أقولك الحقيقة: **مفيش نظام في الدنيا أمانه 100%** — لا أوبر ولا أمازون ولا البنوك. اللي موجود فعلاً هو:

- **تقليل الاحتمال**: كل ثغرة معروفة يكون ليها إجراء مضاد مكتوب.
- **تقليل الأثر**: لو حصلت مشكلة، مفيش خسارة بيانات ومفيش خسارة فلوس.
- **سرعة الاكتشاف والرجوع**: تعرف إن فيه مشكلة قبل العميل ما يكلمك، وترجّع النظام لحالته في دقايق.

الوثيقة دي مبنية على المبدأ ده. وكل مرحلة فيها **بوابة (Gate)** — ممنوع نعدي للمرحلة اللي بعدها قبل ما نعدي البوابة. ده اللي هيدي الاستقرار الحقيقي، مش الوعود.

## 1. قواعد العمل بينّا (الاسكربت الحرفي)

### 1.1 دورة العمل الثابتة لكل خطوة

كل خطوة في المشروع بتمشي بنفس الـ 6 مراحل دي، من غير استثناء:

```
1. TICKET     → نكتب الخطوة كتذكرة فيها: الهدف، المدخلات، المخرجات، شروط القبول
2. DESIGN     → نتفق على الشكل (Schema / API contract / UI) قبل أي سطر كود
3. BUILD      → التنفيذ على branch منفصل
4. TEST       → اختبارات آلية + اختبار يدوي حسب checklist
5. REVIEW     → مراجعة كود + مراجعة أمان
6. RELEASE    → نشر على staging → موافقة → نشر على production
```

**قاعدة ذهبية:** أي خطوة مش عندها "شروط قبول" مكتوبة بالأرقام = خطوة ممنوع تبدأ.

### 1.2 بطاقة استعادة السياق (انسخها وابعتها لو نسيت السياق)

> **السياق:** مشروع `baytak` — منصة خدمات منزلية في مصر.
> نشتغل بملفين مرجعيين: `01-master-plan.md` (الخطة) و `02-data-dictionary.md` (قاموس البيانات والـ API).
> الستاك: NestJS + PostgreSQL + Redis + Flutter + Next.js.
> إحنا حالياً في: **المرحلة \_\_ / السبرنت \_\_ / الخطوة رقم \_\_**.
> آخر حاجة خلصناها: \_\_\_\_\_\_.
> المطلوب دلوقتي: \_\_\_\_\_\_.
> قواعد ثابتة: أسماء الجداول والأعمدة `snake_case`، الكود `camelCase`، الـ API routes `kebab-case`، كل الأسعار بالقرش (integer)، كل الأوقات UTC، كل جدول فيه `id, created_at, updated_at, deleted_at`.

### 1.3 قواعد التسمية (ثابتة ومقدسة — مينفعش تتغير بعد ما نبدأ)

| العنصر | القاعدة | مثال |
|---|---|---|
| اسم الجدول | `snake_case` + جمع | `service_orders` |
| اسم العمود | `snake_case` + مفرد | `total_amount_cents` |
| المفتاح الأساسي | `id` (UUID v7) | `id` |
| المفتاح الأجنبي | `<اسم الجدول مفرد>_id` | `technician_id` |
| القيم المنطقية | `is_` / `has_` | `is_active`, `has_warranty` |
| التواريخ | `_at` | `accepted_at` |
| المبالغ | `_cents` (integer) | `commission_amount_cents` |
| الحالة | `status` + enum | `order_status` |
| ملف الكود | `kebab-case` | `service-order.service.ts` |
| الكلاس | `PascalCase` | `ServiceOrderService` |
| المتغير | `camelCase` | `totalAmountCents` |
| متغير البيئة | `UPPER_SNAKE` | `DATABASE_URL` |
| مسار الـ API | `kebab-case` + جمع | `/api/v1/service-orders` |
| Git branch | `type/ticket-desc` | `feat/BYT-102-order-create` |
| رقم التذكرة | `BYT-<رقم>` | `BYT-102` |

### 1.4 قواعد بيانات ثابتة على مستوى المشروع كله

1. **كل المبالغ integer بالقرش** — ممنوع `float` نهائياً في أي حاجة فلوس.
2. **كل الأوقات مخزّنة UTC** (`timestamptz`)، والعرض بتوقيت القاهرة في الواجهة بس.
3. **مفيش حذف نهائي** — `deleted_at` (soft delete) لكل جدول فيه بيانات أعمال.
4. **كل جدول** فيه: `id`, `created_at`, `updated_at`, `deleted_at`.
5. **كل عملية حساسة** (فلوس، صلاحيات، حالة طلب) تتسجل في `audit_logs`.
6. **كل طلب API يغيّر بيانات** لازم يقبل `Idempotency-Key` header.
7. **الأرقام المعروضة للعميل** كود قابل للقراءة: `ORD-2026-000123` مش الـ UUID.

## 2. المعمارية والستاك التقني

### 2.1 المبدأ المعماري: Modular Monolith أولاً

مش هنبدأ بـ Microservices. ده أكبر غلط بيقتل الستارت أب في مصر — تعقيد بلا فايدة.

```
نبدأ: Modular Monolith (تطبيق واحد مقسّم داخلياً لموديولات مستقلة)
     ↓ (عند 50 ألف طلب/شهر أو فريق أكبر من 8 مطورين)
نفصل: أول خدمة تتفصل = Notifications، بعدها Matching، بعدها Payments
```

كل موديول داخلي له مجلد مستقل وحدوده واضحة، فالفصل بعدين يبقى ساعات مش شهور.

### 2.2 الستاك المعتمد

| الطبقة | الاختيار | السبب |
|---|---|---|
| Backend | **NestJS (TypeScript)** | معماري ومنظّم، سهل توظيف عليه في مصر |
| Database | **PostgreSQL 16** | موثوق، يدعم PostGIS للمواقع، JSONB للمرونة |
| Cache/Queue | **Redis** + **BullMQ** | جلسات، rate limit، طوابير المهام |
| البحث الجغرافي | **PostGIS** | إيجاد أقرب فني |
| Realtime | **WebSocket (Socket.io)** | تتبع الفني + الشات |
| تطبيقات الموبايل | **Flutter** | كود واحد لـ iOS + Android، أسرع وأرخص |
| لوحة الإدارة | **Next.js + shadcn/ui** | سريعة والفريق نفسه يقدر يشتغل عليها |
| التخزين | **S3-compatible** (AWS S3 / DigitalOcean Spaces) | الصور والمستندات |
| الاستضافة | **AWS أو DigitalOcean** (منطقة قريبة: فرانكفورت / البحرين) | زمن استجابة معقول لمصر |
| الدفع | **Paymob** (أساسي) + **Fawry** (احتياطي) | الأشهر والأنسب للسوق المصري |
| الخرائط | **Google Maps SDK** | دقة العناوين في مصر |
| الإشعارات | **Firebase Cloud Messaging** | مجاني وموثوق |
| SMS/OTP | مزوّد محلي (Victory Link / SMSMisr) | التسليم داخل مصر |
| المراقبة | **Sentry** + **Grafana/Prometheus** + **UptimeRobot** | أخطاء + مقاييس + توفر |
| CI/CD | **GitHub Actions** | مجاني وكافي |

## 3. البيئات وخط النشر

### 3.1 ثلاث بيئات (إلزامي من اليوم الأول)

| البيئة | الاستخدام | البيانات | من يدخلها |
|---|---|---|---|
| `local` | تطوير على جهاز المطور | بيانات وهمية | المطور |
| `staging` | اختبار قبل النشر | نسخة مموّهة من الإنتاج | الفريق + أنت |
| `production` | العملاء الحقيقيون | حقيقية | نشر آلي فقط |

**قاعدة:** ممنوع منعاً باتاً أي مطور يدخل على قاعدة بيانات الإنتاج مباشرة. أي تعديل يمر عبر migration مراجَع.

### 3.2 خط النشر (CI/CD)

```
push على branch
  → lint + type-check
  → unit tests (يجب ≥ 70% تغطية للموديولات المالية)
  → integration tests
  → security scan (npm audit + secret scanning)
  → build
  → deploy تلقائي على staging
  → موافقة يدوية منك
  → deploy على production (blue-green: من غير انقطاع)
  → smoke tests تلقائية
  → لو فشلت: rollback تلقائي خلال 60 ثانية
```

## 6. التفصيل الحرفي — المرحلة 1 (MVP) — 4 أشهر

نمشي بسبرنتات أسبوعين. كل سبرنت مخرجه **شغّال ومنشور على staging**.

### S1 — الأساس (أسبوعان)
- إعداد المشروع، قاعدة البيانات، الـ migrations الأولى
- نظام المصادقة: تسجيل برقم موبايل + OTP، JWT + refresh token rotation
- نظام الصلاحيات RBAC (`super_admin`, `ops_manager`, `support_agent`, `finance`, `customer`, `technician`)
- Health check + logging + Sentry
- **شرط القبول:** مستخدم يقدر يسجل ويدخل ويجدد التوكن. اختبارات المصادقة كلها خضراء.

### S2 — الكتالوج والعناوين
- تصنيفات وخدمات وأسعار (سباكة، كهرباء، تكييف، تنظيف)
- إدارة العناوين + اختيار على الخريطة + التحقق من نطاق التغطية
- **شرط القبول:** العميل يضيف عنوان ويشوف الخدمات المتاحة في منطقته فقط.

### S3 — إنشاء الطلب
- إنشاء طلب: خدمة + عنوان + وقت + وصف + صور
- حساب السعر التقديري + رسوم الكشف
- حالات الطلب الكاملة (state machine مقفولة: أي انتقال غير مسموح = خطأ)
- **شرط القبول:** طلب يتخلق ويظهر في لوحة الإدارة خلال ثانية.

### S4 — التوزيع والمطابقة (Matching)
- إيجاد الفنيين المؤهلين (خدمة + منطقة + متاح + مستوى)
- إرسال الطلب على دفعات (أقرب 5 → 10 ثواني → الدفعة التالية)
- قبول/رفض + منع التعارض (أول واحد يقبل ياخده — قفل ذري)
- **شرط القبول:** 100 طلب متزامن من غير تعيين مزدوج ولا مرة.

### S5 — تطبيق الفني
- استقبال إشعار، عرض التفاصيل، قبول، ملاحة
- تحديث الحالة: في الطريق → وصلت → بدأ → خلص
- رفع صور قبل/بعد
- **شرط القبول:** دورة كاملة من التطبيق الحقيقي على جهاز حقيقي.

### S6 — التتبع المباشر والشات
- WebSocket لموقع الفني (كل 10 ثواني، يقف بعد اكتمال الطلب)
- شات نصي + صور بين العميل والفني (يقفل بعد 24 ساعة من الإنهاء)
- **شرط القبول:** التتبع يشتغل على 3G ضعيف من غير ما يستهلك البطارية بشكل مبالغ.

### S7 — الدفع والفاتورة
- كاش + محفظة + كارت (Paymob)
- الفاتورة النهائية = رسوم الكشف + قطع الغيار + أجر العمل − الخصم
- تسوية العمولة تلقائياً في محفظة الفني
- **Idempotency** على كل عملية دفع
- **شرط القبول:** 50 عملية دفع تجريبية من غير خطأ واحد في الحسابات. مطابقة محاسبية 100%.

### S8 — التقييم والشكاوى والصرف
- تقييم بعد الإنهاء + تعليق
- فتح شكوى + دورة حياتها + الاسترجاع
- طلب صرف أرباح الفني + دورة موافقة مالية
- **شرط القبول:** شكوى تُفتح وتُحل وتُسترجع الفلوس بشكل صحيح.

### S9 — لوحة الإدارة الكاملة
- إدارة الفنيين والمستندات والموافقات
- متابعة الطلبات لحظياً + تدخل يدوي (إعادة تعيين، إلغاء، تعديل سعر)
- التقارير: طلبات/إيراد/عمولة/تقييم/شكاوى
- **شرط القبول:** موظف العمليات يشتغل يوم كامل من اللوحة بدون مطور.

### S10 — التقوية (Hardening) — أسبوعان كاملين
- Rate limiting على كل endpoint
- اختبار اختراق أساسي (OWASP Top 10)
- اختبار حِمل: 500 مستخدم متزامن
- النسخ الاحتياطي + **تجربة استرجاع فعلية**
- Runbooks: إيه اللي نعمله لو وقع السيرفر / بوابة الدفع / قاعدة البيانات
- **شرط القبول:** استرجاع كامل لقاعدة البيانات من نسخة احتياطية في أقل من 30 دقيقة، مُجرَّب بالفعل.

### S11 — الإطلاق التجريبي المغلق (Closed Beta)
- 50 عميل + 15 فني في حيّ واحد
- كل طلب فيه متابعة هاتفية من فريق العمليات
- **شرط القبول:** 100 طلب مكتمل، تقييم ≥ 4.3، إلغاء < 10%.

### S12 — الإطلاق العام في الحيّين
- تسويق محدود جغرافياً
- **بوابة المرحلة 1:** 500 طلب مكتمل، شكاوى < 5%، تكرار الطلب من نفس العميل ≥ 25%.

## 7. الأمان — القائمة الإلزامية

### 7.1 المصادقة والصلاحيات
- OTP لـ 6 أرقام، صلاحية 5 دقائق، 5 محاولات كحد أقصى، حظر 15 دقيقة
- Access token 15 دقيقة، Refresh token 30 يوم مع **تدوير** (لو اتسرق يبطل)
- RBAC على مستوى كل endpoint + فحص ملكية المورد (العميل يشوف طلباته هو بس)
- 2FA إجباري لكل حسابات لوحة الإدارة

### 7.2 البيانات
- **ممنوع تخزين بيانات الكروت نهائياً** — توكن من بوابة الدفع فقط (PCI DSS)
- تشفير الأعمدة الحساسة (`national_id`, `bank_account_number`) بـ AES-256
- تشفير قاعدة البيانات at-rest + TLS 1.3 في النقل
- إخفاء البيانات في السجلات (لا رقم موبايل كامل ولا OTP في الـ logs)
- صور المستندات في bucket خاص بروابط موقّتة (15 دقيقة)

### 7.3 التطبيق
- Rate limiting: 60 طلب/دقيقة للمستخدم، 5/دقيقة لإرسال OTP
- التحقق من كل مُدخل (DTO validation) + منع SQL Injection عبر ORM
- SSL pinning في تطبيقات الموبايل
- كشف الأجهزة المكسورة (root/jailbreak) لتطبيق الفني
- منع انتحال الموقع (mock location) لتطبيق الفني

### 7.4 المال
- Idempotency key إجباري على كل عملية دفع
- كل حركة مالية في `wallet_transactions` بنظام القيد المزدوج (المجموع لازم يساوي صفر)
- الصرف للفنيين بموافقة بشرية فوق مبلغ معيّن
- مطابقة يومية آلية مع كشف بوابة الدفع، وأي فرق ينبّه فوراً

### 7.5 التشغيل
- `audit_logs` لكل عملية إدارية
- تنبيه فوري عند: فشل دفع متكرر، محاولات دخول فاشلة، تغيير صلاحيات
- مراجعة أمنية خارجية قبل كل مرحلة كبيرة

## 9. نظام الجودة — قلب المشروع

فكرة المستويات اللي كتبتها هي فعلاً الميزة التنافسية. دي طريقة تحويلها لنظام.

### 9.1 المستويات

| المستوى | شرط الوصول | مضاعف السعر | الأولوية في التوزيع |
|---|---|---|---|
| 🥉 Bronze | فني جديد معتمد | 1.00× | أخيرة |
| 🥈 Silver | 25 طلب + تقييم ≥ 4.2 + شكاوى < 8% | 1.10× | متوسطة |
| 🥇 Gold | 100 طلب + تقييم ≥ 4.5 + شكاوى < 4% + التزام مواعيد ≥ 90% | 1.25× | عالية |
| 💎 Platinum | 300 طلب + تقييم ≥ 4.7 + شكاوى < 2% + التزام ≥ 95% + اجتياز اختبار الأكاديمية | 1.45× | الأعلى + طوارئ |

### 9.2 معادلة نقاط الجودة (تتحسب أسبوعياً)

```
quality_score = (avg_rating / 5 × 40)
              + (on_time_rate × 25)
              + (completion_rate × 20)
              + ((1 - complaint_rate) × 15)
```

المراجعة كل أسبوع. الترقية فورية، والتنزيل بعد إنذارين موثقين — عشان الفني يحس بالعدل مش بالتعسف.

### 9.3 مسار قبول الفني (Funnel)

```
تقديم → فحص مستندات (بطاقة + محل إقامة) → فحص جنائي (فيش وتشبيه)
     → اختبار عملي في التخصص → تدريب سلوكي يوم واحد
     → 5 طلبات تحت إشراف → اعتماد كامل
```

**قاعدة:** معدل القبول المستهدف 20–30%. لو بتقبل 80% من المتقدمين، إنت مش بتفلتر — وده هيموّتك بعد 6 شهور.

## 11. النموذج المالي (تقديرات — تحتاج تأكيد بأرقام حقيقية)

### مصادر الدخل (بترتيب الأولوية)
1. **عمولة على الطلب** — 15–20% (المصدر الأساسي، من اليوم الأول)
2. **اشتراك الفنيين** — بعد إثبات القيمة، لا قبل
3. **عقود الشركات والكومباوندات** — هامش عالي، مرحلة 4
4. **رخص برامج المغاسل والورش** — SaaS، مرحلة 3
5. **الضمان المدفوع** — مرحلة 7
6. **الإعلانات داخل التطبيق** — آخر حاجة، وبحذر شديد لأنها بتضر التجربة

### ملاحظة صريحة على العمولة
15–20% في مصر تعتبر مرتفعة بالنسبة لدخل الفني. الفني هيحاول يشتغل خارج المنصة. الحلول: أسعار أعلى للمستويات الأعلى، تدفق طلبات ثابت، صرف أسبوعي سريع، وميزات مالية (سلف، تقسيط أدوات). **الفني مش مورد — هو عميلك التاني.**

## 14. رأيي الصريح على الخطة

**الأقوى فيها:** نظام المستويات، والتفكير في الشركة كشركة تشغيل مش تطبيق، والترتيب التدريجي للمراحل. دي عقلية مؤسس صح.

**اللي محتاج تعديل:**
1. **9 مراحل كتير على 5 سنين.** لو خلصت المرحلة 1 و2 و3 بجودة عالية، تكون بنيت شركة محترمة. المراحل 5 و6 و8 ممكن تتأجل من غير خسارة.
2. **الذكاء الاصطناعي (P5) مبكر.** التشخيص بالصورة صعب ودقته المنخفضة هتضر ثقة العميل. أجّله لما يبقى عندك آلاف الصور الحقيقية من طلباتك — ساعتها هيبقى عندك ميزة حقيقية مش خدعة.
3. **الإعلانات داخل التطبيق فكرة سيئة في البداية.** بتضر تجربة المستخدم وعائدها ضئيل قبل ملايين المستخدمين.
4. **الـ Marketplace (P6) يتعارض مع نظام الجودة.** لما تفتح لأي شركة تسجّل، بتفقد التحكم في الجودة — اللي هو ميزتك الوحيدة. لو عملتها، اعملها بمعايير قبول أصعب من الفني الفردي.
5. **الأهم اللي ناقص: كيف تجيب أول 100 عميل؟** مفيش خطة استحواذ في الوثيقة. أقوى قناة في مصر لمشروع زي ده: اتفاقيات مع إدارات الكومباوندات وشركات إدارة الأملاك. عميل واحد من دول = 200 وحدة سكنية.

**الحكم:** الفكرة قابلة للتنفيذ بشكل كبير، والسوق فيه فراغ حقيقي. التنفيذ التشغيلي — مش الكود — هو 80% من المعركة.
