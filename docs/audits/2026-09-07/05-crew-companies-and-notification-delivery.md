# الطاقم والشركات وضمان وصول التحديثات

Baseline: `a77013b5`. فحص قراءة فقط. لا نغير سياسة المهلة/إلغاء Work Opportunity التي اختارها المالك؛ العيوب هنا تتعلق بمسارات تقبل إنشاء شيء ثم لا تسمح بإكماله، أو تتجاوز حراسًا موجودين.

## AUD-025 — P1 BUG: مسارات إضافة الطاقم لا تفرض نفس التخصص/النطاق

- الدليل: `apps/api/src/modules/orders/technician-order-execution.controller.ts:468` ما زال يعرض POST `:id/team-members` الذي ينادي `OrderTeamService.addMember` عند `order-team.service.ts:222`. يفحص قائد الطلب ونمط TEAM والشركة والعدد فقط، ثم يحفظ العضو عند `:259`؛ لا فحص تخصص معتمد أو مدينة أو إتاحة أو قبول طلب إضافي.
- مسار التجنيد الحديث يملك حارس التخصص/المدينة عند `order-team.service.ts:377`، لكنه لا يُستعمل في المسار القديم. كذلك `apps/api/src/modules/orders/admin-orders.service.ts:1334` في `validateCrewCandidateOrThrow` يفحص اعتماد profile والجدول، لا اعتماد تخصص الخدمة/نطاق المدينة. عضو LIGHT يضاف مباشرة من `addCrewMember` عند `:1388` دون المرور بحارس التخصص الحديث.
- السيناريو: عضو شركة تخصصه كهرباء يضاف عبر endpoint القديم إلى سباكة، أو مساعد خارج مدينة الطلب يضاف إداريًا بينما التجنيد الحديث كان سيرفضه. المسار القديم أيضًا يسمح بفني مشغول لأن شركة واحدة ليست دليل إتاحة.
- الحل المقترح: بوابة أوامر طاقم واحدة لكل العملاء، مع اختلافات صلاحيات صريحة فقط. أوقف مسار الإضافة القديم أو اجعله adapter للحارس الحديث. الاستثناء الإداري، إن أراده المالك، يكون مُعلنًا بصلاحية وسبب وحدود، لا تجاوزًا ضمنيًا. لا توسيع نطاق الفني القائد إلى سياسة المدينة الخاصة بالمساعد بالخطأ.
- اختبارات القبول: كهرباء/سباكة، مساعد خارج المدينة، زون أخرى داخل المدينة، اعتماد مرفوض، عضو محجوز، عبر API الشركة والأدمن والتجنيد؛ نفس نتيجة الحارس حسب الدور.

## AUD-026 — P1 BUG: تعديل الطاقم غير ذري ويمكن بعد التسوية

- الدليل: `apps/api/src/modules/orders/order-team.service.ts:568` يقرأ العدد والقدرة ثم يحفظ عند `:630` دون transaction/قفل طلب أو عامل. `addMember` عند `:222` و`removeMember` عند `:262` لا يتحققان من orderStatus أصلًا. مسار قبول الفرصة يقفل الطلب عند `:677` لكنه يفحص TEAM والقائد فقط، لا حالة نهائية.
- `apps/api/src/modules/orders/admin-orders.service.ts:1387` يقرأ ويفحص خارج transaction ثم يضيف؛ إزالة الطاقم عند `:1454` تحذف دون حارس حالة. unique `(order_id, technician_id)` يمنع الشخص المكرر لنفس الطلب، لكنه لا يمنع إضافة شخصين مختلفين فوق العدد ولا إضافة نفس الشخص لطلبين متعارضين.
- السيناريوهات: قائدا طلبين يجندان نفس العامل وهو LIGHT في اللحظتين؛ طلب مساعد اختياري واحد يتلقى طلبين متزامنين لشخصين؛ إزالة عضو بعد أن بدأ العمل أو بعد التسوية تغير الطاقم الظاهر ومصدر حساب الحصص بينما الحقوق التاريخية قائمة.
- الحل المقترح: lifecycle واضح لضم/انسحاب/استبدال العضو، قفل الطلب والعامل وإعادة الفحص داخل transaction مشتركة مع السعة والتسوية. لا حذف عضوية تاريخية بعد استحقاقها؛ تسجيل إنهاء مشاركة/تعديل مؤرخ ومسار تعويض إذا لزم. بعد التسوية الطاقم المالي immutable.
- اختبارات القبول: سباق ضم لنفس العامل بطلبين؛ آخر خانة لمرشحين؛ remove مقابل settle؛ قبول فرصة لطلب مكتمل/ملغي. المخرجات لا تتجاوز العدد/السعة ولا تخرج شخصًا من حقه بتغيير سجل التشغيل.

## AUD-027 — P2 BUG: فرصة المساعد الاختياري في طلب فردي لا يمكن قبولها

- الدليل: `apps/api/src/modules/orders/order-team.service.ts:544` يسمح بالتجنيد عند `optionalAssistantSlots>0` حتى لو لا مساعد مطلوب إلزاميًا. `recruitMember` عند `:636` ينشئ فرصة إذا العامل لديه حمل `MEANINGFUL` بدل الإضافة المباشرة. لكن `acceptCrewOpportunity` عند `:681` يشترط `bookingMode===TEAM`، وعند `:706` يرفض المساعد إذا `missingAssistants<=0` دون احتساب الخانة الاختيارية.
- السيناريو: طلب فردي يسمح بمساعد واحد اختياري، والمساعد لديه شغل آخر غير متقاطع في اليوم نفسه. تصله فرصة صحيحة بحسب الإنشاء، ثم القبول يفشل: إما الطلب ليس TEAM أو «العدد اكتمل» رغم أن الخانة الاختيارية فارغة.
- الحل المقترح: تعريف واحد للخانة المتاحة يستخدمه إنشاء الفرصة وقبولها والأدمن والواجهة؛ يحسب required وoptional دون خلطهما. تطبيق الحماية ضد زيادة العدد داخل القفل. لا حل بتحويل الفردي كله إلى TEAM أو إلغاء شرط موافقة العامل على الشغل الإضافي.
- اختبارات القبول: optional assistant + MEANINGFUL يستطيع القبول إذا متاح زمنيًا؛ إذا امتلأت الخانة بين العرض والقبول يُرفض برسالة صحيحة؛ لا يتاح مساعد مجاني لإعادة زيارة ممنوعة بالسياسة.

## AUD-028 — P1 BUG: نقل ملكية الشركة المتزامن قد ينتج مالكين بصلاحيات فعلية

- الدليل: `apps/api/src/modules/technicians/technician-companies.service.ts:569` يقرأ المالك والشركة والمالك الجديد قبل transaction؛ transaction عند `:572` تحفظ الشركة والأدوار دون إعادة قراءة مقفلة/مقارنة version. `requireOwner` عند `:154` يثق في `profile.teamRole===OWNER` ولا يطابق `company.ownerUserId`.
- السيناريو: المالك A يرسل نقلًا إلى B ونقلًا إلى C بالتوازي. كلا الطلبين يرى A مالكًا؛ كلاهما يحوّل هدفه إلى OWNER ويحوّل A إلى MANAGER. الشركة تشير لآخر هدف، لكن B وC يمكن أن يبقيا OWNER في profiles؛ وكلاهما يجتاز requireOwner لاحقًا.
- الحل المقترح: قفل الشركة والملفات المعنية بترتيب ثابت وإعادة فحص المالك الفعلي؛ مصدر ملكية authoritative واحد وأدوار مشتقة متسقة. نقل واحد يفوز والآخر stale/conflict. نفس نمط قفل target مطلوب في addStaff عند `:456` الذي يفحص companyId ثم يحفظ منفصلًا حتى لا تقبله شركتان في اللحظة نفسها.
- اختبارات القبول: A→B مقابل A→C؛ نقل مقابل إزالة/تغيير دور؛ إضافتان لعضو مستقل من شركتين. مالك واحد يتطابق في company/profile والصلاحيات وسجل التدقيق.

## AUD-029 — P2 BUG: صندوق إشعارات المشاريع يعلن delivered حتى إذا فشل الإرسال

- الدليل: `apps/api/src/modules/notifications/notifications.service.ts:193` و`:198` يحفظان FAILED ويعيدان الصف دون رمي exception. `apps/api/src/modules/notifications/project-notification-outbox.processor.ts:108` ينادي `notifyMultiChannel` ولا يفحص نتائج القنوات ثم يكتب delivered عند `:124`.
- أثر restart: `notifications.service.ts:137` يعيد أي صف موجود لـsourceOutboxId فورًا حتى لو QUEUED/FAILED. إذا توقف السيرفر بعد إنشاء الصف وقبل dispatch، إعادة معالجة outbox لا تحاول تسليم الصف مرة ثانية. البحث في وحدة notifications لم يجد كاسحًا عامًا يستأنف QUEUED/FAILED ليغطي هذه الفجوة.
- الأثر: بطاقة المتابعة توحي باكتمال التسليم بينما push لم يصل، وإعادة المحاولة الصورية لا تعالج الفشل. وجود إشعار in-app لا يعني وصول تنبيه خارجي؛ قد يكون مقبولًا كسياسة، لكن يجب تسمية النجاح الجزئي وعدم الادعاء بوصول القناتين.
- الحل المقترح: فصل إنشاء إشعار idempotent عن محاولات تسليمه؛ تسجيل نتائج القنوات وتوقيت retry/backoff وmanual-review، وعدم إعادة إرسال قناة نجحت. فشل القناة المعطلة عمدًا لا يُعاد بلا نهاية. define متى يعتبر outbox مكتملًا وما الذي يعتبر best-effort.
- اختبارات القبول: فشل FCM مع نجاح in-app؛ timeout؛ crash بعد إدراج QUEUED؛ retry لا يكرر الصندوق ولا يترك القناة المطلوبة بلا محاولة؛ لوحة الأدمن تعرض partial/failure بصدق.

## AUD-030 — P2 BUG/GAP: حدث تغيير الطاقم يبث قبل commit وبعض أحداث المال بلا سجل تسليم دائم

- دليل مباشر: `apps/api/src/modules/orders/order-team.service.ts:732` يبث `ORDER_CREW_CHANGED_EVENT` داخل transaction قبول الفرصة، قبل خروجها. listener عند `apps/api/src/modules/notifications/listeners/order-crew-changed-notification.listener.ts:23` ينشئ إشعارًا باستخدام service مستقلة، لا manager العملية.
- السيناريو: الإشعار/refresh يصل ثم يفشل commit، فيرى العامل «اتضفت» وهو غير مضاف. وحتى عند نجاح commit، المستمع قد يقرأ الحالة قبل أن تظهر عضوية الطاقم على اتصاله.
- الاتجاه العكسي: أحداث الموافقة/الاسترداد تُبث بعد commit في `inspection-quote.service.ts:887` و`payments.service.ts:3382`؛ هذا يمنع إشعار rollback لكنه يترك فجوة crash بين الالتزام والبث. لا يوجد outbox عام لهذه العمليات مثل الموجود للمشاريع. لا نصف كل إشعارات التطبيق بأنها مفقودة؛ هذه نافذة تعطل محددة.
- الحل المقترح: event/outbox مع العملية نفسها، مستمعون idempotent، وبث realtime بعد commit. التصحيح المرحلي لنقطة crew ينقل البث خارج transaction، والحل الدائم يضمن استعادته بعد restart. استخدم event identity ونسخة aggregate لمنع إعادة ترتيب الحالة القديمة فوق الحديثة.
- اختبارات القبول: فشل commit لا ينشئ إشعار نجاح؛ crash بعد commit لا يضيّع إشعار المعاينة/الاسترداد؛ إعادة التنفيذ لا تضاعف الإشعارات أو تعيد حالة UI قديمة.
