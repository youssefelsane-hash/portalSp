# إقفال تنفيذ أوديت العمليات الجوهرية

**الفرع:** `codex/implement-aud-001-007`  
**نقطة الأساس:** `a77013b5`  
**النطاق:** تنفيذ ملاحظات AUD-001 إلى AUD-030، مع تنظيف C1-C4. لا يغير هذا السجل بيانات تاريخية أو يفترض نجاح بوابة دفع خارجية.

## قاعدة التنفيذ

- كل أثر مالي يكتب حالته والحركة المحلية وسجل التدقيق داخل معاملة واحدة، أو يحجز صف `processing` قابلًا للمراجعة بدل إعلان نتيجة غير مؤكدة.
- الحجز، المدة، الطاقم، والمطابقة يقرأون المصدر التشغيلي نفسه؛ لا يمكن لمدخل قديم أن يستبدل مخرجات معادلة حديثة.
- الإشعار ليس دليلًا على نجاح العملية. أحداث المال وتذكيرات الكاش والمسارات الحساسة تستخدم صندوق تسليم دائم، retries idempotent، ثم `manual_review` عند استنفاد المحاولات.

## تنظيف المصادر المتنافسة

- **C1:** لا إنشاء جديد لـV1. النسخة 2 هي default ثابت، وإعداد cutover القديم صار قراءة تاريخية فقط: `7c02c5e0`.
- **C2:** القراءة التاريخية لـV1 بقيت مقيدة بالحفاظ على حقوق طلبات سابقة؛ لا توجد كتابة جديدة أو واجهة إعداد تسعير ثانية.
- **C3:** يوم العمل موحد عبر إعداد لا يتجاوز 12 ساعة، وسعة الجدولة، وتعلم الإنتاجية: `d09bc0b2`.
- **C4:** منافذ الطاقم تمر بالحارس الموحد، ومسار تذكير الكاش القديم داخل الذاكرة أزيل بعد استبداله بصندوق دائم: `d435b10c`, `2b64851a`, `ded17a0c`.

## تحقق من الكود

- نجح بناء API بعد التغييرات الأخيرة: `nest build`.
- نجح بناء لوحة الإدارة الإنتاجي: `npm --workspace apps/admin run build`.
- نجحت اختبارات مركزة أثناء التنفيذ: `legacy-earnings-settings-guard.spec.ts` و`recurring-card-payment-collection.spec.ts`.
- توجد اختبارات regression مع كل حزمة حساسة (الدفع المتكرر، refunds، KPI، quotes، السعة، الطاقم). بيئة التطوير المحلية الحالية لا تملك schema migrations الأحدث، لذلك لا تُسجّل نتيجة integration كاملة كنجاح زائف.

## قبل الإنتاج

يلزم تشغيل migrations `0289` إلى `0291` على قاعدة معزولة، ثم اختبار sandbox حتمي للبوابة: timeout بعد تنفيذ خارجي، webhook متأخر/مكرر، refund غير معروف ثم reconciliation يدوي، وnotification retry. يجب أيضًا اختبار 2 ساعة + 2 ساعة، 15 ساعة، عقد شهري، عرض صور مع فني premium، ودفع إضافي بعد دفعة أصلية على Android والويب.
